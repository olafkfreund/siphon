# Spec: Portal: a proper, usable UI, with editing

Mockups: `docs/mockups/portal.html`. This is one static file with every
screen. Open it in a browser; the screen tabs at the top switch between
them. **The mockups are part of this spec and are approved with it.**

## Design

### 1. Look and feel ("fresh, modern, engaging")

- **Visual style.**
  - Light-first, with a dark theme that follows `prefers-color-scheme`, plus
    a manual toggle remembered in `localStorage`.
  - The background is soft off-white (dark: deep slate). Content sits on
    white cards with a 14 px radius and a soft shadow.
  - Generous spacing on an 8 px grid, and a system UI font stack: no web
    font download, and it is CSP-safe.
- **Colour.** The accent is **indigo-violet** (`#6E56F8`) with a teal
    success (`#14B8A6`), amber for waiting (`#F59E0B`) and rose for failure
    (`#F43F5E`). Every colour is a CSS custom property in one `:root` token
    block and its dark override, so the palette is one edit.
- **Brand.** A logo mark, an inline SVG of a gateway arch with a spark,
  next to the wordmark "agentgw". No external assets.
- **Status pills.** Each state has an icon, a label and a colour, so state
  never relies on colour alone:
  - queued ◷
  - running ⟳, which spins (reduced-motion respected)
  - waiting for approval ✋
  - done ✓
  - failed ✕
  - denied / cancelled ⊘
- **Engaging, not noisy.**
  - Toasts after actions.
  - A soft highlight on rows that just changed state.
  - Friendly empty states with an illustration-free icon and one call to
    action ("Add your first source").
  - A **flow view** for each rule: three linked nodes (source → condition
    → action) with the source type and action kind as icons.
  - Small transitions only, all disabled under `prefers-reduced-motion`.
- **Layout.**
  - Desktop: a left sidebar for navigation (Dashboard, Jobs, Approvals with
    a count badge, Rules, Sources, Agents, Routines, Logins, Egress,
    Audit, Settings/History).
  - Phone: the sidebar collapses into a top bar with a menu button, and
    tables become stacked cards. Approve and Deny are full-width buttons on
    a phone.
- **Accessibility.**
  - Contrast meets WCAG AA in both themes.
  - Focus rings are visible, and every input has a label.
  - Keyboard: `g d` / `g j` / `g r` jump to pages (optional), and `/`
    focuses search.
  - htmx swaps announce changes through an `aria-live` region.

### 3. Editing: an overlay on the config file (intent Q6 a)

- **Storage.** New migration with two tables:
  - `config_item(kind TEXT, name TEXT, yaml TEXT, deleted INTEGER, updated_at, PRIMARY KEY(kind,name))`
  - `config_revision(id INTEGER PRIMARY KEY, at, actor, summary, items_json, diff)`
  - `kind` is one of `sources`, `rules`, `agents`, `routines` or
    `credentials`. No other kind is accepted. `server`, `limits` and `units`
    can never be edited here.
- **Effective config.** agentgw reads the file as a YAML node tree, then
  applies the overlay:
  - map kinds (`sources`, `agents`, `routines`, `credentials`): set or
    remove the key;
  - `rules`, a list keyed by `name`: replace in place, append, or remove.

  The result is marshalled and fed through the existing `config.Parse`,
  `Validate` and `Warnings`. **There is exactly one parser and one
  validator.** File-relative paths (`db`) resolve as today.
- **Provenance.** Each item is marked `file`, `portal` or `override` (both)
  for the badges and for "Reset to file", which deletes the overlay row.
- **Save flow.**
  1. The form or YAML tab posts one item.
  2. The server builds the candidate effective config and validates it.
  3. If invalid, the form comes back with the errors placed on their
     fields. Nothing is stored.
  4. If valid, the diff is shown. "Confirm" then writes the item, writes a
     `config_revision` (full overlay snapshot plus unified diff of the
     effective YAML, secrets as refs), writes the audit row
     `config_changed`, and applies the change.
- **Concurrency.** Each editor carries the revision number it started from.
  Saving against a newer revision gets "changed since you opened it",
  with a reload offered.
- **Restore.** Restoring a revision replaces the overlay with that
  snapshot, which is itself saved as a new revision, after validation.
- **Export.** `agentgw config export -config f` prints the effective YAML
  (refs, not secret values) for git or Nix. The portal's History page
  offers the same download.
- **Startup.** `serve`, `run-once` and `validate` all load the effective
  config (file plus overlay). If the overlay makes the config invalid, for
  example because a file change removed a source a portal rule uses:
  - `serve` starts with **the file config plus the last valid overlay
    revision**, logs the error, and shows a red banner in the portal;
  - `validate` reports the error;
  - `validate -file-only` checks just the file.

### 4. Applying without a restart

- **Atomic swap.** `job.Pipeline` keeps the config in an
  `atomic.Pointer[config.Config]` with a `Config()` accessor. Every existing
  `p.Cfg` read goes through it; `web` does the same through an accessor
  passed in `Options`. `Apply(newCfg)` swaps it.
- **Pollers restart.** The poller set restarts as a group: a context per
  generation, cancelled and respawned for the new source list, keeping
  `source_state`.
- **Webhook map.** The webhook map is rebuilt on apply.
- **Running and queued jobs are untouched.** They already snapshot actions
  and agents in their payload. MCP sources stay live, as today.
- **Egress.** The proxy needs nothing: allowlists are computed per run from
  the job's agent snapshot.
- **Fail-safe.** `Apply` happens only after `Validate` succeeds. A changed
  credential store path is not possible: `server.*` can't be edited.

### 5. Secrets in the portal

- **Secret fields** (webhook `secret`, source `auth.bearer`, source headers
  marked secret, credential `api_key`) accept one of:
  - an `env:` or `file:` reference;
  - **a value.** A value is written to `<state dir>/secrets/<kind>-<name>-<field>`
    (0600, the directory 0700), and the item stores
    `file:<that path>`. The value is never read back into a page. The
    field shows "•••• set (stored)" and offers "replace".
- **Logins.** "Add login" posts to the same code path as
  `agentgw credentials import`, then shows metadata only.
- **Masking.** All secret values stay in `cfg.Secrets()` for masking, as
  today.

### 6. The rule tester

- **The event.**
  - Each source's last event (the payload after `for_each` source
    extraction, capped at 64 KiB) is stored in the existing, unused
    `source_state.json` column on each poll or webhook.
  - Fields whose names match secret patterns (`token`, `secret`,
    `password`, `authorization`, `api_key`, `cookie`) are redacted before
    storing.
  - The tester defaults to that event, or the user pastes JSON (with
    optional headers).
- **The run.** The tester uses the same code as `agentgw rules test`: a
  dry-run `HandleEvent` on an in-memory store with the candidate rule, and
  renders the agent prompt (`action.RenderPrompt`), the argv or the unit.
  It never enqueues or executes anything.
- **htmx.** `hx-post` to `/rules/test` with `hx-trigger="input changed delay:400ms"`.

### 7. Live updates

- **Polling only the parts that change.** The current whole-`main` 5 s
  poll is replaced by per-fragment polling:
  - dashboard tiles, the "needs you" list and recent jobs every 5 s;
  - the job detail header and output every 2 s while running, then
    stopped;
  - the approvals badge in the sidebar every 10 s.
- **Editors never poll,** so typing is never interrupted (today's
  whole-page poll would wipe a form).

### 8. Implementation shape

- **Templates.** `internal/web/templates/` gets `layout.html` (sidebar,
  topbar and toast region), partials (`pill`, `flow`, `empty`,
  `secret-field`, `diff`) and one template per page. The same
  `html/template` setup is kept.
- **Static assets.** `static/style.css` holds the tokens, components and
  utilities, about 20–30 KB unminified, hand-written. `static/app.js`
  (small, no framework) handles the theme toggle, copy buttons, the
  toast dismiss, the menu toggle, argv and step list add/remove/reorder,
  and keyboard shortcuts. htmx is kept. CSP stays `default-src 'self'`:
  there are no inline scripts or styles, and SVG icons go in a sprite at
  `static/icons.svg`.
- **Go.**
  - `internal/config/overlay.go`: merge, provenance and export.
  - `internal/store` migration and queries for items and revisions.
  - `internal/web` handlers per kind (list, form, validate, diff, save,
    delete, reset) on shared generic helpers. The form ↔ struct mapping
    is explicit per kind; the YAML tab covers everything else.
  - `job.Pipeline.Apply`.
  - `cmd/agentgw`: `config export`, and loading the overlay in `serve`,
    `run-once` and `validate`.
- **API.** JSON API parity for the new write paths (`/api/config/...`), so
  the CLI or other tools can use them. They use the same bearer token and
  the same validation.

## Alternatives rejected

- **The portal writing the YAML file:** impossible on NixOS (the file is in
  the Nix store), and it fights declarative config. Rejected in the intent
  (Q6).
- **A DB-only config, with the file as a seed:** breaks the "config in git
  or Nix" workflow and makes the file lie after the first edit.
- **A JS framework (React/Svelte) or a build step:** rejected by the intent
  constraints. htmx plus a small `app.js` covers the interactions.
- **Tailwind or Pico:** Tailwind needs a build step. Pico's classless
  defaults would be fought at every turn for this custom look.
  Hand-written tokens are smaller and fully controlled.
- **Web fonts:** a fetch to an external origin breaks the CSP. Bundling Inter
  (OFL) adds about 300 KB for little gain over the system stack. This can
  be revisited.
- **Server-sent events for live updates:** long-lived connections and more
  code. Targeted polling is enough at this scale.

## Risks

| Risk | Mitigation |
|---|---|
| A bad edit breaks running automation | Validation before apply; apply is atomic; restore any revision; startup falls back to the last valid overlay |
| File and overlay drift (a Nix change removes a source a portal rule uses) | Startup fallback + red banner naming the broken item; provenance badges; "reset to file"; export to fold overlay into the file |
| Portal token theft now allows creating agents and cmd actions | Accepted in the intent (Q8): the sandbox, egress and audit bound it; units allowlist, server and limits stay out of reach; every change is audited with a diff and reversible. Roles are a follow-up (Q9) |
| Secrets leaking into the page, the diff, the export or the audit | Values are stored as files and only refs travel; tests assert no stored value appears in any response, revision, diff or export |
| Hot apply races (a poller using the old config while jobs read the new one) | Each poll and job reads one `Config()` snapshot for its whole run; the pollers generation is restarted after the swap |
| The last-event store keeps sensitive payloads | Size cap, key-pattern redaction, lives in the 0700 state DB like job payloads today |
| A big UI diff regresses the existing pages | Existing web tests kept, new handler tests per page, and a headless smoke test (see Verification) |

## Verification

- **Unit tests.**
  - Overlay merge for every kind, including rules by name, tombstones,
    provenance, the refusal of `server`, `limits` and `units`, and export
    round-tripping through `Parse` unchanged.
  - Revision and restore.
  - Stale-revision conflict.
  - Startup fallback to the last valid overlay.
  - The secret-field value is stored in a 0600 file, and the value never
    appears in HTML, the diff, the export or the audit.
  - Last-event redaction.
  - The tester never enqueues anything.
- **Handler tests.** Every page renders. Each write route needs CSRF, and
  validation errors come back as field errors. The CSP header is unchanged,
  and there is no inline script or style in any template (a test greps the
  templates).
- **Apply.** A test proves a rule added through the portal fires on the next
  event without a restart, and a removed source stops polling.
- **Visual check.** A Chrome session against the local instance
  (`~/.local/state/agentgw-dev`) screenshots each page in light and dark
  and at phone width, compared with the approved mockups. The owner then
  clicks through.
- **Existing gates.** `go test -race ./...`, `devenv test` and the NixOS VM
  test all stay green. The VM test gains one subtest: a rule created over
  the JSON API fires without a restart.
