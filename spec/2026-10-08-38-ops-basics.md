# Spec: ops basics (backup and restore, metrics, retention)

## Design

**Summary:** this adds three independent pieces, none of them on the job path:
- two local commands that archive and restore Siphon's runtime state;
- an authenticated Prometheus endpoint, computed from the database at
  scrape time;
- retention settings read by the existing daily cleanup.

The NixOS module gains an optional backup timer. There is no migration.

### What "state" is

Everything lives next to `server.db` (`filepath.Dir(db)`):

| Path | What | Source |
|---|---|---|
| `<db>` (+ `-wal`, `-shm`) | the overlay and its revisions, jobs, approvals, audit, notifications | `internal/store` |
| `secrets/` | pasted secret values, one file each | `secretsDir`, `internal/web/forms.go:170` |
| `credentials/` | subscription logins (`<name>/auth.json`, …) | `internal/cred/cred.go:28` |

Not included (resolved question 3):
- `siphon.yaml`, `server.token`, `actions_dir` (per-run scratch);
- the lock file;
- anything else in the directory.

### `siphon backup create`

```
siphon backup create [-config f | -db path] <file|->
```

- **Local command** (`Mode: "local"`, like `credentials import`). It
  needs only the db path: `-db` names it directly, otherwise `-config`
  is loaded for `server.db`. This lets it run on NixOS without knowing
  where the generated `siphon.yaml` is
  (`sudo -u siphon siphon backup create -db /var/lib/siphon/state.db …`).
- **Runs against a live daemon.**
  1. Open the db with its own connection, no lock taken.
  2. `VACUUM INTO '<tmpdir>/state.db'`. SQLite gives a transactionally
     consistent snapshot that includes the WAL, while the daemon keeps
     writing.
  3. `tmpdir` is `os.MkdirTemp(dir(db), ".backup-*")`, mode 0700, and is
     removed on every exit path.
- **The archive** is a gzip'd tar with these entries, in this order:
  1. `siphon-backup.json`: `{"format": 1, "version": "<siphon version>",
     "schema": "<newest applied migration>", "created": "<RFC 3339>"}`.
  2. `state.db`: always this name, whatever `server.db` is called.
  3. `secrets/…` and `credentials/…`: regular files and directories only.
     Symlinks, devices and anything else are skipped with a warning that
     names the path.
- **Output.** A file target is written to `<file>.tmp-<rand>`, created
  `O_EXCL` with mode 0600, then fsynced and renamed into place. The
  archive is never visible with looser permissions or half-written. An
  existing `<file>` is refused unless `--force` is given. `-` writes to
  stdout for `| age -r … > x.age` or `| restic backup --stdin`. Stdout is
  refused when it is a terminal.
- **Ordering:** the db is snapshotted first, then the directories are
  read. If a secret is added or removed between the two steps:
  - an added secret is an unreferenced file, which does no harm;
  - a removed secret means the restored overlay references a missing
    file, and `siphon validate` names it after the restore.

  Both need an edit in the same second as the backup, which is accepted
  and documented.
- **Output text** is one line on stderr: the path, the size, and the
  number of secrets and logins. No file contents and no secret names
  beyond the counts.

### `siphon backup restore`

```
siphon backup restore [-config f | -db path] [--yes] <file|->
```

- **Offline only.** It takes `store.Lock(db)`
  (`internal/store/store.go:374`). If the daemon holds the lock, it
  exits 5 (conflict): "siphon is running: stop it first".
- **Runs as the owner.** The process's euid must own `dir(db)`.
  Otherwise it exits 1: "run as the user that owns <dir>
  (sudo -u siphon …)". Restoring as root would leave files the daemon
  can't read.
- **Validates before touching anything.** The archive is extracted to a
  0700 temp dir in `dir(db)`.
  - **Entry names:** an absolute path, a `..` element, a symlink or
    hardlink, an entry outside `siphon-backup.json`, `state.db`,
    `secrets/` and `credentials/`, or a duplicate name rejects the whole
    archive.
  - **Size:** a total size cap of 1 GiB rejects the whole archive.
  - **Manifest:** a missing or unknown `format` rejects it. So does a
    `schema` newer than this binary's newest migration: "backup is from
    a newer siphon (<version>)".
  - **Database:** `state.db` must open and pass
    `PRAGMA integrity_check`.
- **Confirms.** If `<db>` already exists, it prints what it will
  replace (the db size and job count, and the secret and login counts)
  and asks y/N on a TTY. Without a TTY it needs `--yes` (exit 2
  otherwise, the same rule as `apply`).
- **Swaps safely.** The current `<db>` (and its `-wal` and `-shm`),
  `secrets/` and `credentials/` move to `dir(db)/pre-restore-<UTC
  timestamp>/`, then the extracted files move into place. Each step is
  a rename within one filesystem. The pre-restore copy is kept and
  printed; deleting it is the operator's job.
- **Permissions:** files are 0600 and directories 0700. Ownership needs no
  change, because the owner check guarantees the right user.
- **Older backups are fine.** Migrations run when Siphon next starts.
- **Afterwards** it prints: "restored; start siphon, then run `siphon
  validate`".

**Command name:** the intent said `siphon restore-backup`. `restore`
already restores a config revision (`cmd/siphon/cli.go:94`). Grouping both
under `siphon backup create|restore` is clearer and fits `credentials
import|ls`.

### `GET /metrics`

- **Auth:** on the main listener, wrapped in `s.api`
  (`internal/web/api.go:129`). That means a bearer login token plus the
  failed-auth rate limit (resolved question 1). In Prometheus:
  `authorization: { credentials_file: /run/secrets/siphon-token }`.
- **Format:** Prometheus text 0.0.4, written by hand with
  `fmt.Fprintf`. It has `# HELP` and `# TYPE` lines and sorted labels.
  There is no client library.
- **Values:** every value is computed from the database at scrape time.
  They are gauges, so a restart loses nothing and there are no
  in-memory counters to keep right. One `internal/store` function runs
  the queries in one read transaction.

| Metric | Labels | Meaning |
|---|---|---|
| `siphon_build_info` | `version` | always 1 |
| `siphon_jobs` | `state` | jobs in the db by state (queued/running/pending_approval are live; done/failed/cancelled cover the retention window) |
| `siphon_jobs_finished_last_hour` | `state` (done, failed, cancelled) | the alerting number: `siphon_jobs_finished_last_hour{state="failed"} > 0` |
| `siphon_queue_oldest_seconds` | — | age of the oldest queued job, 0 when none |
| `siphon_approvals_pending` | — | jobs in pending_approval |
| `siphon_approval_oldest_seconds` | — | age of the oldest pending approval, 0 when none |
| `siphon_agent_runs_today` / `siphon_agent_runs_daily_limit` | — | the daily cap and its use (`CountAgentJobsSince`) |
| `siphon_source_failing` | `source` | 1 when a polled source has `failing_since` set |
| `siphon_source_last_poll_timestamp_seconds` | `source` | `last_poll_at` |
| `siphon_rule_error` | `rule` | 1 when a rule has a stored error (`rule_error`) |
| `siphon_notifications` | `channel`, `state` | outbox rows by state (pending = retrying) |

- **Labels:** only names from the config. Sources, rules and channels
  are operator-chosen and bounded. There are no job ids, event values,
  URLs or errors.
- **Removed items:** a label whose source, rule or channel is no longer
  in the running config is dropped. This keeps a deleted item from
  showing as failing forever.
- **Docs:** a Prometheus scrape config and four example alerts: a failed
  job, an old approval, a failing source, and a stuck outbox.
- **Cost:** about eight small indexed queries per scrape, on SQLite.
  That's fine at a 15–60 s scrape interval.

### Retention

```yaml
server:
  retention:
    jobs: 720h          # finished jobs, their approvals and notifications (default 720h = 30 days)
    audit: 720h         # the audit log (default 720h)
    seen_events: 168h   # webhook/each dedupe ids (default 168h = 7 days)
```

- **Where it lives:** `server.retention` is operator-only. `server.*`
  is not an overlay kind (`Kinds`, `internal/config/overlay.go:42`), so
  no overlay change is needed.
- **Units:** values are Go durations, the same `Duration` type as every
  other duration in the config. There is no new `d` unit.
- **Defaults:** unset or `0` means today's value.
- **Minimums:** below `24h` is a validation error ("retention.jobs must
  be at least 24h"):
  - the `seen_events` minimum keeps webhook re-deliveries from re-firing;
  - the `audit` minimum keeps the log from being cleared by mistake.
- **No "forever":** there's no explicit setting for it. A large value
  such as `87600h` does the job.
- **Code:** `store.Cleanup(db, now)` becomes
  `store.Cleanup(db, now, store.Retention{Jobs, Audit, Seen})`. The
  constants at `internal/store/store.go:283` become the defaults. The
  notification-pruning rows use the jobs cutoff, as now. The pipeline
  passes the config value (`internal/job/queue.go:159`).
- **Reload:** a config reload takes effect at the next daily run. Nothing
  else changes.

### NixOS module

```nix
services.siphon.backup = {
  enable = false;                 # resolved question 5
  dir = "/var/backup/siphon";     # created 0700 siphon:siphon by tmpfiles
  calendar = "daily";             # OnCalendar
  keep = 7;                       # newest N archives kept
};
```

- **The unit:** `siphon-backup.service` (oneshot, `User=siphon`,
  `ReadWritePaths=[dir]`, the same hardening as the main unit where it
  applies) runs:
  1. `siphon backup create -db ${stateDir}/state.db
     ${dir}/siphon-$(date -u +%Y%m%dT%H%M%SZ).tar.gz`;
  2. then deletes all but the newest `keep` `siphon-*.tar.gz` files in
     `dir`.
- **Timer:** `siphon-backup.timer` has `Persistent = true` and a
  randomised delay of 10 min.
- **Restore** has no unit. It is a documented manual step: stop the
  service, run `sudo -u siphon siphon backup restore …`, start the
  service.

## Alternatives rejected

- **Copying the files instead of `VACUUM INTO`.** Copying the db, `-wal`
  and `-shm` while the daemon writes can tear the copy. The backup API
  (`sqlite3_backup`) isn't exposed by `database/sql` without driver
  specifics. `VACUUM INTO` is one SQL statement and also compacts the
  copy.
- **A `GET /api/backup` endpoint, or a portal download button.** These
  would hand every secret to anyone holding the login token, over the
  network (resolved question 4).
- **Encryption in the archive (age).** It adds a key to manage and lose
  (resolved question 2). Stdout output makes piping to age or restic
  one line.
- **In-memory Prometheus counters** (`_total`). They would need
  instrumenting every place a job changes state, and would reset on
  restart. Gauges from the db are always right, and the
  `_last_hour` gauges cover alerting.
- **The `prometheus/client_golang` library.** It is a large dependency
  tree for a few dozen lines of text output.
- **A separate unauthenticated metrics listener.** It needs a new port,
  and data is exposed if it's bound wrongly (resolved question 1).
- **Retention in the overlay (portal-editable).** Shortening audit
  retention from the portal would let a portal user erase the trail of
  what they did.
- **Online restore.** Swapping the db under a running daemon corrupts it,
  or gets undone by its next write.
- **Including `siphon.yaml`.** It belongs to the operator's config
  management (resolved question 3). A restored archive with an old
  `siphon.yaml` could also silently undo Nix-managed settings.

## Risks

- **The archive leaks secrets** if it's mishandled after creation. That
  is outside Siphon's control. Mitigations:
  - 0600 from creation;
  - a refusal to write to a TTY;
  - a docs warning, with the age/restic pipe shown first.
- **The `VACUUM INTO` disk cost:** it needs free space equal to the db
  next to it (the temp dir is in `dir(db)`, so it's on the same
  filesystem). A full disk fails the backup cleanly (the temp dir is
  removed) and never touches the live db.
- **Restore leaves a stale `-wal` if interrupted.** Every step is a
  rename and the old files are kept in `pre-restore-*`. An interrupted
  restore can be completed by hand from there, and the docs say how.
- **Metrics scrape load.** It is bounded by the query count. A scrape
  under the rate limit with a wrong token gets 401s and then 429s, the
  same as the API.
- **NixOS:** the timer unit is new and off by default. Existing hosts see
  no change until they set `backup.enable`. No production host is
  changed by this work.

## Verification

- **Unit tests:**
  - **`internal/store`:** a snapshot taken while another connection
    writes opens and has every committed row. Cleanup honours custom
    retention. The metrics query returns the expected gauges on a seeded
    db.
  - **`cmd/siphon`:**
    - create then restore round-trips the db, secrets and credentials,
      with modes 0600/0700;
    - restore refuses while the lock is held, and refuses archives with
      `..`, an absolute path, a symlink, an unknown entry, a newer schema
      or a corrupt db;
    - `--yes` is needed without a TTY;
    - an existing target is refused without `--force`;
    - stdout to a TTY is refused.
  - **`internal/config`:** the retention defaults, and the 24h minimum
    as a validation error.
  - **`internal/web`:** `/metrics` returns 401 without a token, returns
    200 in the text format with one, and has no label outside the
    config names.
- **VM test (`nix/vm-test.nix`), new subtest:**
  1. Create a rule and a pasted secret.
  2. Start `siphon-backup.service` (timer enabled in the test node) and
     check that an archive exists with mode 0600.
  3. Check that `backup restore` refuses while siphon runs.
  4. Stop siphon, delete the state, restore, start siphon, and check
     that the rule and the secret's `file:` ref are back and
     `siphon validate` passes.
  5. Check `/metrics` with and without the token.
- **OCI test:** `backup create -db /data/state.db -` inside the
  container produces a readable archive.
- **Gates:** `go vet ./... && go test -race ./...`, `nix flake check`
  (VM test), and the OCI test in CI.
