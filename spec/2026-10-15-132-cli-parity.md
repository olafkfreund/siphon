# Spec: the CLI can do what the portal does

## Design

The principle: **every new API endpoint serves the same function the portal
page already calls,** so the two can't drift apart. Every new CLI command
goes through the existing client (`internal/client`) and the `cmd/siphon`
conventions.

1. **Deleting a login.** `siphon connect login --name <n> --logout [--yes]`
   calls the existing `DELETE /api/connections/logins/{name}`
   (`internal/web/connapi.go:144`). It uses the same removal and audit entry
   as the portal.
   - Without `--yes`, it asks for confirmation on a TTY and refuses
     otherwise (exit 2).
   - A 404 exits with 4.
   - `siphon delete credentials <n>` prints a hint pointing to this command
     when a stored login exists, because it doesn't remove the stored login.
2. **Remote export.** `siphon config export` goes over
   `GET /api/config/export` when no `-config` is given; with `-config` it
   stays local. To do this:
   - take `config` out of `localOnly`;
   - extend the existing `-config` check in `clientMode`
     (`cmd/siphon/cli.go:31`), which `jobs`, `approve` and `deny` already
     use.

   The output is the YAML, or `{"yaml": …}` with `-o json`.
3. **Job detail and approvals.**
   - `GET /api/jobs/{id}?detail=1` returns `s.jobDetail(id)`
     (`internal/web/pages.go:60`), with JSON tags on `jobView`. Its
     `*config.Agent` field is serialised as the agent's name only.
   - `siphon jobs show <id> --detail` prints it. The MCP `job` tool gets a
     `detail` bool.
   - `GET /api/approvals` adds `kind`, `target`, `source` and `source_type`
     to each row, from `s.approvalActions` (`portal.go:60`). Old clients
     ignore the extra fields.
   - `get approvals` shows a WHAT column.
4. **Egress.** `GET /api/egress` returns `s.egress()` (`pages.go:255`),
   with JSON tags on `egressView`, `egressList` and `egressBlocked`.
   `siphon get egress` works because `egress` is added to `listKinds`, which
   the MCP `get` tool picks up too.
5. **Notion verification.**
   - `GET /api/sources/{name}/notion-verification` returns
     `{"token", "at"}` with `Cache-Control: no-store`. It returns 404 when
     nothing is pending.
   - `siphon connect notion <source> [--yes]` shows the token, asks for
     confirmation unless `--yes`, and POSTs it to the existing endpoint
     (`notion.go:67`). If the token changed in the meantime, the server's
     exact-match check gives a 409, which exits with 5.
   - The token is never logged; it is shown once, because the user has to
     paste it into Notion.
6. **Dashboard.** `GET /api/dashboard` returns
   `{counts, total, running, failed, agent_runs, agent_cap, success_rate}`
   for the last 24 hours. It is built by refactoring `s.dashboard`
   (`data.go:322`): the numbers move into a helper both callers use, and the
   greeting stays portal-only.
   - `siphon status` adds a "Last 24h" line.
   - With `-o json`, the result gets a `last_24h` object.
7. **Testing an unsaved rule.** `POST /api/rules/{name}/test` accepts an
   optional `rule` field: rule YAML that is tested instead of the saved
   rule. It is validated against the current config, the same way the
   portal's `runRuleTest` (`editors.go:287`) does; the shared part goes into
   a helper both use.
   - The command is `siphon test -f rule.yaml [event.json|-] [--last]`.
     The rule's name comes from the file.
8. **MCP tools** (`cmd/siphon/mcp.go`), each calling the same client
   function as its CLI command:
   - `enable` and `disable` (`rule`): dry-run unless `--allow-write`;
   - `reset` (`kind`, `name`): dry-run unless `--allow-write`;
   - `history` (optional `kind`/`name` or `rev`): read-only;
   - `restore` (`rev`): `--allow-write` only;
   - `catalog` (optional `category`): read-only;
   - `get`: gains `notifications` and `egress`, and passes the audit filters
     `rule`, `event`, `since` and `limit`.

   Approve/deny and connect stay out of MCP.
9. **Docs.**
   - `go generate ./docs` regenerates `cli.md`.
   - docs/llm.md lists the new MCP tools.
   - docs/troubleshooting.md mentions `jobs show --detail` and
     `get egress`.

## Alternatives rejected

- **Role-scoped API tokens (viewer, operator):** a design change, not
  parity. It would be a separate issue if wanted.
- **Parsing `/metrics` for the dashboard numbers:** Prometheus text is a
  worse contract than JSON.
- **Exposing approve/deny through MCP:** AGENTS.md forbids it.
- **A new `siphon delete login` verb:** `connect login --logout` already
  exists for OAuth, and keeping login lifecycle under `connect` is
  consistent.

## Risks

- **Serialising `jobView` to JSON** could leak something the template only
  shows masked. The job detail already masks event and output at build
  time, but the review must check every new JSON field, especially the
  rendered prompt and the event, against what the portal shows.
- **The Notion token** reaches a terminal. Admins already see it in the
  portal; `no-store` stops proxies caching it.
- **The `test -f` path** must not save anything. It reuses dry-run
  evaluation.
- **#131 edits the same docs and cli.go usage line.** Rebase after #131
  merges.

## Verification

- Unit tests, one or more per point, in `internal/web/*_test.go`
  (handlers) and `cmd/siphon/*_test.go` (commands against an httptest
  server). For example:
  - logout removes the store entry and the key file, and a 404 exits 4;
  - export over the API matches the local export;
  - `?detail=1` includes the steps and has no unmasked secret;
  - egress JSON;
  - the Notion GET has the `no-store` header and a 404 when nothing is
    pending;
  - dashboard numbers;
  - `test -f` doesn't save;
  - each MCP tool's write gate.
- `go vet ./... && go test -race ./...`, and `go generate ./docs` leaving a
  clean diff.
- An Opus review of the diff against the plan.
