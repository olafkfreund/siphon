# Spec: Mattermost outgoing webhooks and slash commands trigger rules

## Design

### Config (`internal/config/config.go`)

The webhook `Source` gains two fields:

```go
TokenField string `yaml:"token_field"` // body-token: the body field holding the token (default token)
ReplyText  string `yaml:"reply_text"`  // body-token: a fixed {"text": …} reply instead of an empty 202
```

**Validation** (the `switch s.Signature` at `config.go:1473`):
- **A new case, `"body-token"`.** `signature_header`, `timestamp_header`
  and `token_header` aren't allowed. `token_field`, if set, must match
  `^[A-Za-z_][A-Za-z0-9_]*$`.
- **Mode-specific fields:** `token_field` and `reply_text` are refused for
  any other signature mode.
- **`reply_text`:** at most 500 characters, and plain text. Mattermost shows
  it as Markdown, which is fine.
- **The default error** lists `body-token`.

The schema is regenerated, and `explain` gets the two fields and the new
enum value.

### Verification (`internal/source/webhook.go`)

`WebhookOptions` gains `TokenField` and `ReplyText`, passed from
`internal/job/hooks.go:32`.

**Body decoding** comes first, for every mode: `decodeBody(r, body)`.
- **A `Content-Type` of `application/x-www-form-urlencoded`** (the media
  type, without parameters) is parsed with `url.ParseQuery`. A key with one
  value becomes a `string`, and a repeated key becomes a `[]any` of strings.
- **Anything else** keeps today's path: `DecodeJSON`, or `{"raw": body}`.
- This replaces the `DecodeJSON` call at `webhook.go:243` and keeps its
  fallback.

**A new case, `"body-token"`,** in the signature switch (`webhook.go:118`):
1. `data := decodeBody(r, body)`, then `field := orDefault(o.TokenField, "token")`.
2. Read `got, _ := data[field].(string)`. A JSON number or a missing field
   counts as missing.
3. **Compare in constant time,** hashing both sides with SHA-256, as the
   `token` mode does. A wrong or missing token gets
   `reject(401, "token missing or wrong")`.
4. **`delete(data, field)`,** so the token never reaches the event.
5. **The replay key** is `sha256(json.Marshal(data))`, taken after the
   delete. Go marshals map keys in sorted order, so the key is stable and
   doesn't depend on the secret.

The decoded, token-free `data` is the event, so the later `decodeBody`
call is skipped for this mode.

**The reply:** when `ReplyText != ""` and the delivery is accepted, the
response is `200`, `Content-Type: application/json`,
`{"text": ReplyText}`. That's what Mattermost's outgoing webhooks and slash
commands display. Duplicates and errors keep their codes (409, 5xx). Every
other mode stays `202` with an empty body.

### Catalog (`internal/catalog/services.yaml`)

The Mattermost entry is replaced: it was the `not-yet` line at `:793`.

```yaml
  - id: mattermost
    name: Mattermost
    mark: MM
    category: chat
    summary: "Outgoing webhooks and slash commands from Mattermost, verified by the token Mattermost generates."
    capabilities: [webhooks]
    status: available
    templates: [mattermost-command-agent]
    fields:
      - {<<: *f_name, default: mattermost}
      - {key: token, label: Token, type: secret, required: true, help: 'Mattermost shows it after you create the outgoing webhook or slash command (Integrations).', section: 2}
      - {key: reply, label: Immediate reply, type: text, help: 'Optional: shown to the user at once, for example "Working on it…".'}
    creates:
      - kind: sources
        name: '{{.name}}-hooks'
        when: 'true'
        hook: true
        yaml: |
          type: webhook
          signature: body-token
          secret: {{secret "token" "secret"}}
          {{- if .reply}}
          reply_text: {{.reply | printf "%q"}}
          {{- end}}
    setup: |
      In Mattermost: Integrations → Outgoing Webhooks (or Slash Commands) → Add.
      Callback URL: the URL above. Save, copy the Token Mattermost shows, and
      paste it here. Slash commands use POST.
```

The setup has a chicken-and-egg problem: Mattermost generates the token
only after the URL is saved. The guide says to connect once the URL is
known: `siphon connect mattermost` prints it after the first save. Check
how the catalog flow orders this against `hook: true`. If the URL needs
the source to exist first, the token field can't be required.

### Generic webhook entry

The generic `webhook` entry's `mode` choices gain `body-token`. In that
mode the `header` field is unused, the token is pasted, and generating one
is allowed, for self-built senders.

### Template: `docs/templates/mattermost-command-agent.yaml`

A slash command `/ask <question>` runs a model agent, and a routine posts
the answer to a Mattermost incoming webhook:
- agent `mattermost-ask`: `kind: model`, `credential: ollama-local`, the
  prompt from `{{.event.text}}` (untrusted), and no tools;
- routine `mattermost-ask-reply`: the `answer` agent step, then `post`,
  which is `cmd: [curl, -fsS, -H, "Content-Type: application/json", --data-raw, "{\"text\": …}", https://mattermost.example.com/hooks/CHANGE-ME]`;
- rule `mattermost-ask`: `on: each`, `cooldown: 30s`, and
  `when: 'event.command == "/ask"'`.

The JSON body must not let `event.text` break out of the string. Build the
reply body as a `cmd` argument whose JSON is encoded by the template
function `json`, if the template func map has one. Otherwise post with
`-F`, a form field, so no quoting applies. The plan picks the one that
exists. The `baseConfig` in `cmd/siphon/describe_test.go` gets
`mattermost-hooks: { type: webhook, signature: body-token, secret: env:AGW_HOOK }`.

### Docs

- `docs/connections/README.md` (generated) lists Mattermost as available.
- The generic webhook docs gain the `body-token` mode, and `docs/llm.md`
  gets a line.
- `go generate ./docs`.

## Alternatives rejected

- **Token in a query parameter** (`?token=`). Mattermost doesn't support
  it, and URLs end up in logs.
- **A Mattermost-specific mode.** `body-token` is generic, and other
  services post a body token too.
- **Leaving form bodies as `raw`.** It makes slash commands unusable in
  rules, and it would need a separate decoder per source.
- **A dynamic reply from the agent.** Mattermost needs an answer within a
  few seconds. The agent's answer goes through an incoming webhook (the
  template). `response_url` can come later.

## Risks

- **Form decoding changes what rules see for existing form-posting webhook
  sources.** It changes from `{"raw": …}` to fields. This is a behaviour
  change for anyone matching `event.raw` on a form body: Slack slash
  commands under `slack` mode. The plan greps the templates and docs for
  `event.raw`. It's documented in the changelog or release note.
- **A token travels in every body.** It can't be rotated without updating
  Mattermost. That's documented.
- **The catalog flow ordering** (URL before token) is noted above. The
  plan verifies it.

## Verification

- **`internal/source` tests:**
  - a form and a JSON body with the right token are accepted, the event has
    no `token` key, and the other fields are decoded;
  - a wrong, missing or numeric token gets 401;
  - a custom `token_field`;
  - a repeated form key becomes a list;
  - `reply_text` gives 200 with JSON `{"text": …}`;
  - a duplicate gives 409;
  - other modes still return 202 with an empty body.
- **Form decoding for a `token`-mode source:** fields, not `raw`.
- **`internal/config` validation cases;** the schema and explain tests.
- **`internal/catalog`:** the Mattermost entry renders, with and without
  the reply.
- **`TestTemplatesValidate`** and the `docs` tests.
- **`go vet ./... && go test -race ./...`.**
- **A manual curl:** a form POST, as Mattermost sends it, to a local Siphon
  fires a rule.
