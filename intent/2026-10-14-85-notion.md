# Intent: Notion page and database events, and Notion tools for agents

## Problem

Notion is "Not yet" in the catalog, for two reasons.

1. **Webhook verification.**
   - When you add a webhook subscription to a Notion integration, Notion
     POSTs a one-time `{"verification_token": "secret_…"}` to the URL. You
     must copy that token from the receiving end and paste it back into
     Notion to activate the subscription.
   - After that, Notion signs every event with
     `X-Notion-Signature: sha256=<hex>`, an HMAC-SHA256 of the body keyed
     with the verification token.
   - Siphon's `sha256` mode already verifies that signature. What's missing
     is the first step. The token arrives *unsigned*, before Siphon has a
     secret, and the user has to be able to see it.
2. **Agent tools.**
   - Notion's hosted MCP server (`https://mcp.notion.com/mcp`) only
     accepts OAuth.
   - Siphon has supported OAuth for remote MCP sources since `mcpoauth`:
     `auth.oauth` with dynamic client registration and a portal "Log in"
     button. Nobody has checked whether that flow works with Notion.

## Proposed outcome

- **A Notion webhook source** that waits for the verification token:
  - **Before a secret is set,** the source accepts exactly the
    verification POST: a JSON object whose only key is
    `verification_token`. It keeps the token for the operator, and answers
    `200`. Anything else gets 401, and nothing is delivered.
  - **The portal** shows the captured token once, on the connection page,
    with a "use this token" button. Pressing it stores the token as the
    source's secret, and the source then verifies `X-Notion-Signature` as a
    normal `sha256` source. The CLI equivalent is
    `siphon connect notion --secret -`.
  - **Once a secret is set,** further verification POSTs are refused like
    any unsigned request.
- **A Notion MCP source:** `type: mcp`,
  `url: https://mcp.notion.com/mcp`, `auth: { oauth: {} }`. Logging in from
  the portal gives agents Notion's search, fetch and page tools.
- **A `notion` catalog entry** creating both, and a template: when a page
  in a database changes, an agent summarises it.

## Affected users and systems

- Notion users.
- `internal/source/webhook.go` (the capture state), `internal/store` (where
  the pending token lives), `internal/web` (showing and accepting it), the
  catalog, docs and templates.
- `mcpoauth` is checked against Notion, and changed only if it has to be.

## Constraints

- **The pending token is shown only to an operator,** and only until it's
  used or replaced. It's stored like other secrets: write-only after
  acceptance.
- **The capture can't be abused to plant a secret.** Accepting the token is
  an explicit operator action, and a wrong token makes Notion's
  verification fail, so it shows up at once.
- **Only one pending token is kept.** A later verification POST replaces it,
  because Notion re-sends when you click "resend".
- **No new dependency.**

## Open questions

- **Should the token be captured automatically, or pasted from Notion?**
  Notion doesn't show the token in its own UI; it only sends it to the URL.
  So Siphon has to capture it. **I'd do the capture with operator
  acceptance, as above.**
- **Should the Notion MCP OAuth check happen in this issue?** It needs a
  Notion workspace to log in to. Do you have one? **If you don't, I'd ship
  the webhook side, and mark the MCP part "not verified" in the catalog
  setup text.**

## Decisions (owner, at approval)

- **The verification token** is captured automatically, and used as the
  secret only after the operator accepts it.
- **No Notion workspace was named.** The webhook side ships; the MCP
  source ships with its setup text marked "OAuth login not yet verified
  against Notion".
