# Intent: portal sign-in with OIDC, and roles

## Problem

The portal and the API have one shared admin token (`server.token`):

- **No partial access.** Anyone who can sign in can do everything:
  - change rules and config;
  - import logins;
  - approve agent runs;
  - read every job's output.
- **No individual accounts.** A team can't give one person read-only
  access, or let an on-call engineer approve runs without letting them
  rewrite the config.
- **The audit log can't say who.** Every portal action is recorded as
  `portal`.
- **The token is shared.** Revoking one person means rotating it for
  everyone, and for every script that uses it.
- **The login is a pasted secret.** That's the weakest step for a tool
  that can start agents and units.

Most teams that would run Siphon already have an identity provider:
Keycloak, Authentik, Google Workspace, Entra ID, or GitHub through Dex.

## Proposed outcome

- **Sign in with SSO.** An operator configures one OIDC provider. The
  portal's login page then offers "Sign in with <provider>". People sign in
  with their own account, and the session carries who they are.
- **Three roles:**
  - **viewer:** reads everything the portal shows except secrets, which it
    never shows anyway;
  - **operator:** a viewer who can also approve and deny jobs, enable and
    disable rules, run `test`/`why`, and start an MCP OAuth login;
  - **admin:** everything, including config edits, logins, notifications
    and services.

  A person's role comes from their provider groups or their email,
  mapped in `siphon.yaml`. A signed-in person who maps to no role is
  refused.
- **The audit log names the person.** Rows say `oidc:alice@example.com`
  instead of `portal`.
- **The admin token keeps working.** It's for the CLI, the API, scripts
  and break-glass access when the provider is down, so nothing that works
  today breaks.
- **The portal shows who you are** (name and role), with a sign-out.
  Controls your role can't use are hidden, and refused by the server
  anyway.

## Affected users and systems

- **Code:**
  - `internal/web` (login, sessions, a role check on every portal route,
    the templates);
  - `internal/config` (`server.oidc`, `Validate`, the schema);
  - the audit actor.
- **Infrastructure:** the NixOS module, for the client secret as a
  credential. The VM test, which needs a stub OIDC provider.
- **Docs:** a how-to for signing in with SSO, the config reference, and
  `llms-full.txt`.
- **Operators** who turn it on. Nobody else: it's off unless configured.

## Constraints

- **Off by default.** Without `server.oidc`, the portal behaves exactly as
  today.
- **Spec-conformant.** Authorization code flow with PKCE, `state` and
  `nonce`.
  - The ID token's signature, `iss`, `aud`, `exp` and `nonce` are verified
    against the provider's discovery document and JWKS.
  - The provider must be https, except for loopback.
- **Roles are enforced on the server,** on every portal route and form
  POST. They aren't only hidden in the templates.
  - The existing CSRF protection stays.
  - A forged or tampered session can't raise a role.
- **Sessions:**
  - signed, as today;
  - they carry the subject, display name and role, and nothing secret;
  - they last at most 12 hours, or 24 as today, whichever is shorter;
  - the provider's tokens are not kept after sign-in.
- **Secrets:** the OIDC client secret is an `env:` or `file:` ref, and it's
  masked. With NixOS, it goes through `services.siphon.credentials`.
- **Egress:** discovery, JWKS and token requests use a guarded client.
  Siphon follows no redirects.
- **The API stays token-only.** Per-user API tokens are out of scope here.
- **Dependencies:** none beyond `golang.org/x/oauth2`, unless the owner
  approves one for ID token verification (question 4).

## Open questions

1. **Roles.** Are viewer, operator and admin the right three? Should
   operator also cover editing rules?
   Recommendation: the three above. Operator doesn't edit rules: rule
   edits change what agents do, so they're an admin action.
2. **Role mapping.** There are two ways to say who gets which role:
   - groups from a claim (default `groups`);
   - explicit emails.

   Recommendation: both, in config:

   ```yaml
   server.oidc.roles:
     admin:    { groups: [siphon-admins], emails: [alice@example.com] }
     operator: { groups: [oncall] }
     viewer:   { groups: [engineering] }
   ```

   The highest matching role wins. No match means the person is refused.
   An email only counts when `email_verified` is true.
3. **The token login form.** Should it stay on the login page when OIDC is
   on?
   Recommendation: yes, below the SSO button. It's the break-glass path,
   and `server.oidc.token_login: false` hides it for operators who want SSO
   only.
4. **ID token verification.** There are three options:
   - **(a)** hand-written JWKS and RS256/ES256 verification on the stdlib
     `crypto` packages;
   - **(b)** `github.com/coreos/go-oidc/v3`, a new dependency, plus
     `go-jose`;
   - **(c)** `github.com/golang-jwt/jwt/v5`, already in our module graph
     through go-sdk's tests, but not yet in our build.

   Recommendation: (b). Signature checks are security-critical, and go-oidc
   is the most widely reviewed Go implementation. It's two modules, which
   this repo would add deliberately, with `vendorHash` updated.
5. **One provider or several?**
   Recommendation: one. Several can come later if anyone asks.
