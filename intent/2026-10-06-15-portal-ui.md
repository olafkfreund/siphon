# Intent: Portal: a proper, usable UI

## Problem

The portal works but looks unfinished. It is browser-default HTML with six
lines of CSS:

- an unstyled login form in a corner;
- plain tables;
- job states as bare words;
- one yellow "badge" style.

The first thing a new user sees is the login page in the screenshot on #15,
and it says "prototype". Usability suffers as well as looks:

- **No overview.** Nothing answers "is it healthy, what needs me, what
  happened recently" at a glance. `/` simply redirects to the job list.
- **States are hard to scan.** Failed, pending-approval and running jobs all
  look the same.
- **Job output is hard to read.** The output, the `egress: blocked …` lines
  and the audit entries are plain text with no structure.
- **No dark mode, and it isn't usable on a phone.** Approving a pending agent
  run from a phone is a real use case.
- **Parts of the system are missing from the portal:**
  - credentials (which logins exist, when they expire, when last refreshed);
  - each agent's effective egress allowlist;
  - source health (last poll, last error).

  These exist only in the CLI or the logs.

## Proposed outcome

1. **It looks like a finished product.**
   - A consistent visual design: a centred login card, a header with
     navigation, clear typography and spacing.
   - Colour-coded state badges (queued, running, pending approval, done,
     failed, denied).
   - Light and dark themes that follow the OS.
2. **A dashboard at `/`.**
   - What needs attention: pending approvals and recent failures.
   - Counts by state over the last 24 h, and today's agent-run count
     against `agent_runs_per_day`.
   - Source health.
   - The most recent jobs.
3. **Approvals are first-class.**
   - A pending job shows what it will do: the agent or command, the rendered
     prompt or argv, and the triggering event.
   - Approve and deny are clear buttons, also on a phone.
4. **Job detail is readable.**
   - State, timing, exit code and attempt.
   - The output in a scrollable monospace panel.
   - Egress-blocked hosts pulled out into their own list, with a hint
     (add to `egress.allow`).
   - Routine steps shown as a list.
5. **Status-only pages for credentials, egress and sources** (read-only, no
   secrets):
   - credentials: name, provider, expiry, last write-back;
   - egress: the effective allowlist per agent and rule, like `validate -v`;
   - sources: type, poll interval, last success, last error.
6. **It stays light.**
   - Still server-rendered `html/template` + htmx, embedded in the binary.
   - No JS build step, no Node toolchain, no external CDN at runtime.
   - It works under the existing strict CSP (`default-src 'self'`).
7. **Tested.** The existing web tests stay green. New pages get handler tests,
   including that no token or credential content ever appears.

## Affected users and systems

- **Everyone using the portal**, mainly operators approving agent runs and
  diagnosing failures.
- **`internal/web`:** templates, `static/` CSS (and possibly a small icon set
  or font), and handlers for the dashboard, credentials, egress and source
  pages.
- **Possibly small read-only helpers** in `internal/store` (counts, source
  status) and `internal/cred` (listing metadata, as `credentials ls` does).
- No change to the API contract, the CLI, the NixOS module or the sandbox.

## Constraints

- **Must:**
  - keep the strict CSP (no inline scripts or styles, no third-party
    origins);
  - keep CSRF on every POST;
  - keep everything inside the single binary;
  - work without JavaScript for the essential paths (log in, approve,
    deny), since htmx only enhances them.
- **Must not:**
  - show secrets (tokens, login contents, proxy credentials, webhook
    secrets);
  - add write actions beyond today's approve, deny, rule enable and rule
    disable (editing config in the portal is out of scope);
  - add a JS framework or a build step.
- **Accessibility basics:** labelled inputs, keyboard navigation, visible
  focus, and contrast that meets WCAG AA in both themes. State must not rely
  on colour alone (icons or text as well).
- **Licence:** any bundled CSS, fonts or icons must be Apache-2.0
  compatible (MIT, OFL or ISC are fine).

## Open questions

1. **Styling approach.** Options:
   - (a) hand-written CSS with design tokens (smallest, full control);
   - (b) a small classless or base framework such as Pico.css (MIT, ~80 KB),
     restyled with tokens;
   - (c) Tailwind, which needs a build step and so breaks the constraint
     unless the CSS is pre-built and committed.

   Proposal: (a).
2. **Visual direction.**
   - Neutral "ops console" (dense, like Grafana or GitHub Actions), or
     friendlier and more spacious?
   - Any brand colour or logo to use? Otherwise a simple wordmark.
3. **Scope of new pages.**
   - Are credentials, egress and sources all wanted in this issue, or the
     dashboard and job and approval polish first, with the status pages in a
     follow-up?
   - Proposal: all in, because they are read-only and small.
4. **Live updates.** The current 5 s htmx polling of the whole page is kept
   but narrowed to the changing parts. Is server-sent events wanted instead?
   Proposal: keep polling (simpler, no long-lived connections).
5. **Mockups first?** Should the spec include a rendered mockup (an HTML
   artifact) of the login, dashboard and job pages for approval before any
   code? Proposal: yes.

## Decisions at approval (2026-10-06)

The owner approved the intent with the proposals above:
1. Hand-written CSS with design tokens.
2. A neutral, dense "ops console" with a simple wordmark (no brand assets);
   adjustable at the mockup review.
3. All the status pages are in scope.
4. Keep htmx polling, narrowed to the parts that change.
5. The spec ships rendered mockups for approval before any code.

## Amendment 1 (status: approved, 2026-10-06): create and edit in the portal; a fresh, engaging look

The owner, after trying the portal: "We need to be able to add things and
edit them using the portal as well. We need a fresh modern look with a
visual look that is easy but engaging as well."

This replaces two parts of the approved intent:
- the constraint "Must not add write actions beyond approve, deny, rule
  enable and rule disable";
- decision 2 (a neutral, dense ops console).

### Problem (added)

Everything an operator configures (sources, rules, agents, routines, egress
allowlists, logins) can only be changed by editing YAML and restarting
agentgw. That is fine for people who live in a text editor and Nix, and a
wall for everyone else.

The project's goal is a gateway that is "easy to configure". Today the
portal can show a rule but not create one, and a typo is found only by
`validate` after a restart.

### Proposed outcome (added and replaced)

8. **Create, edit and delete from the portal:**
   - sources (MCP, HTTP, webhook);
   - rules (source, condition, firing mode, cooldown, action);
   - agents (kind, login, prompt, MCP sources, allowed tools, limits,
     egress extras);
   - routines (ordered steps).

   Forms guide the user:
   - pickers for existing sources, agents and logins;
   - inline validation with the same checks as `agentgw validate`;
   - a live **rule tester** that runs the condition against the source's last
     event or a pasted sample, showing match or no match and the rendered
     prompt or argv, before saving.
9. **Changes apply without a restart.** Saving validates the whole config and
   swaps it in atomically. A change that fails validation is never applied.
   Running and queued jobs keep their snapshot.
10. **Every change is safe to make and to undo.**
    - The user sees a diff before saving.
    - Each saved change is a numbered revision with who, when and what in the
      audit log.
    - Any earlier revision can be restored in one click.
    - Export to YAML at any time, the same format as the file.
11. **Logins from the portal.** Import a subscription login or API key by
    pasting it into a field. It is written straight to the credential store
    and never displayed again. The page shows only metadata.
12. **A fresh, modern, engaging look** (replaces "neutral ops console"):
    - a clean, light-first design with a dark theme, generous spacing,
      rounded cards, a confident accent colour and a simple logo mark;
    - a visual **flow view** of each rule as source → condition → action;
    - friendly empty states that lead the user to "add your first source";
    - small, purposeful motion such as state changes and toasts;
    - still fast, accessible and readable on a phone.

### Constraints (added and replaced)

- **The config file stays the source of truth wherever it is declared.**
  - On NixOS the file comes from Nix and is read-only.
  - Portal edits must not silently diverge from it, and must survive
    restarts and rebuilds (open question 6).
- **Some settings are never editable from the portal:**
  - the units allowlist (it starts privileged systemd units);
  - `server.*` (listen, token, sandbox, egress listen and socket, DB);
  - limits.

  These stay in the file or Nix config, so a stolen portal session can't
  widen the host's privileges.
- **Secrets are write-only in the portal.** Webhook secrets and source auth
  are entered as `env:`/`file:` references, or as a value stored in
  agentgw's state directory (0600, never shown). Logins go straight to the
  credential store.
- **Every write is guarded.** It is CSRF-protected, validated server-side,
  audited with a diff, and requires the portal token (unchanged auth).
  Multiple users and roles are out of scope (open question 9).
- **Still the same technology.** Server-rendered `html/template` + htmx, the
  strict CSP, and no JS build step. A small amount of hand-written JS, served
  from `/static`, is allowed for the flow view and form helpers if needed.

### Open questions (added)

6. **Where portal edits live.** Options:
   - (a) **An overlay in the state DB, layered on top of the file.** The file
     (or Nix) defines the base. The portal adds or overrides named items,
     and items from the file are marked "from file" (editable as an
     override, or read-only).
   - (b) **The portal writes the YAML file itself.** Simple, but impossible
     on NixOS (store path), and it fights declarative config.
   - (c) **The DB is the source of truth, and the file only seeds it on first
     start.**

   Proposal: (a). It works the same on NixOS, the microVM, the container
   and locally; `agentgw config export` turns the overlay back into YAML for
   people who want it in git or Nix.
7. **Items defined in the file: read-only in the portal, or overridable?**
   Proposal: overridable, with a clear "overrides file" badge and a "reset
   to file" button.
8. **`cmd` actions from the portal.** A portal user can then run any command
   in the sandbox. Allow it, or allow only agents, units from the allowlist,
   and routines? Proposal: allow it. The sandbox, egress and audit already
   bound it, and the portal token is already full admin.
9. **Users and roles** (viewer, approver, editor). Out of scope here, and a
   follow-up if wanted? Proposal: out of scope.
10. **Look and feel.** Any reference you like (for example Linear, Vercel,
    Railway, n8n, Raycast) and a preferred accent colour? The spec will ship
    mockups for approval either way.

### Decisions at approval of Amendment 1 (2026-10-06)

The owner approved the amendment with the proposals:
- Q6 (a): an overlay in the state DB on top of the file, plus
  `agentgw config export`.
- Q7: file items can be overridden, with a badge and "reset to file".
- Q8: `cmd` actions are allowed from the portal.
- Q9: users and roles are out of scope (a follow-up).
- Q10: no reference was given. The spec proposes the look in its mockups.
