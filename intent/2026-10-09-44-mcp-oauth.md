# Intent: OAuth login for MCP sources

## Problem

Siphon is built to treat an MCP server as an event source and as an agent's
scoped toolset. It can only authenticate to a remote MCP server with static
credentials:
- `auth.bearer`;
- fixed `headers`.

Each MCP client builds its transport from them:
- `internal/source/mcp.go:198`, for polling;
- `internal/agentloop/loop.go:368`, for agent tool calls;
- `internal/job/pipeline.go:448`, which hands the headers to agent runs.

Many hosted MCP servers don't take a pasted token. They use the MCP
authorization flow:
- OAuth 2.1 with PKCE;
- discovery through protected-resource and authorization-server metadata;
- dynamic client registration;
- short-lived access tokens with refresh tokens.

Linear, Notion and Atlassian are examples, and more servers switch every
month. Today a user can't connect them at all, or has to copy a short-lived
token out of another client and paste it again every hour.

go-sdk v1.8.0, already our dependency, provides the client side of this
flow:
- `auth.AuthorizationCodeHandler`;
- `oauthex`, for discovery and registration;
- `StreamableClientTransport.OAuthHandler`.

It does not provide two things Siphon needs:
- somewhere to keep the tokens across restarts;
- a way for a person to log in to a daemon that has no browser.

## Proposed outcome

- **Log in once.** An operator connects an OAuth-protected MCP server by
  pointing a source at its URL and logging in once:
  - from the portal (a "Log in" button on the source);
  - or from the CLI (`siphon connect login <source>`), which prints a URL to
    open.

  After consent, the source polls, and agents that list it get its tools.
- **Kept fresh.** Siphon stores the client registration and the tokens with
  its other logins (`credentials/`), refreshes the access token before it
  expires, and keeps working across restarts without another login.
- **Loud when it stops working.** When the refresh token is revoked or
  expires:
  - the source shows as failing, with "log in again";
  - the operator gets the existing "source failing" notification (#36);
  - `siphon why` and the portal say what to do.
- **Agent runs.** An agent run that uses the source gets a valid access
  token for that run, as it gets `auth.bearer` today.
- **Included everywhere.** Backups and restores include the OAuth logins,
  because they live in `credentials/` (#38).

## Affected users and systems

- **Code:**
  - `internal/source` (the MCP poller);
  - `internal/agentloop` and `internal/job` (the tokens for agent runs);
  - `internal/cred` (storage);
  - `internal/config` (the source's auth settings, `Validate`, the schema);
  - `internal/web` (the login start and callback, the source page);
  - `cmd/siphon` (`connect login`).
- **Infrastructure:** the NixOS module and VM test, which need a stub OAuth
  server for the test.
- **Docs:** a how-to for connecting an OAuth MCP server, the catalog, and
  `llms-full.txt`.
- **Operators** of hosted MCP servers. No one on bearer or header auth is
  affected.

## Constraints

- **Secrets stay in the store.**
  - Tokens and client secrets live only in `credentials/`, mode 0600.
  - They never reach logs, job output, the audit log, metrics, the API or
    the portal. Masking covers them.
  - An agent run gets only the access token for the sources it lists, never
    the refresh token.
- **Spec-conformant.**
  - PKCE with S256 is required.
  - `state` and RFC 9207 `iss` are checked.
  - The resource indicator (RFC 8707) is sent.
  - Tokens are bound to the MCP server they were issued for. A token for one
    source is never sent to another URL.
  - Any redirect away from the source's origin drops the Authorization
    header.
- **Existing egress rules.** OAuth discovery, registration and token
  requests use the existing egress client with its private-address rules.
  An authorization server on a private address needs
  `server.services.private_endpoints`, like any other.
- **Login is a person's action.**
  - The daemon never opens a browser or blocks a poll waiting for consent.
  - A missing login is a source error, not a hang.
  - Starting a login needs the admin token. The callback is single-use,
    bound to the `state` it issued, and expires after 10 minutes.
- **No breaking change.** Sources on `auth.bearer` or `headers` behave
  exactly as before.
- **Sandbox.** `sandbox: none` and the OCI image work the same.
- **No new dependency** beyond go-sdk and `golang.org/x/oauth2`. go-sdk
  already pulls that in. Check it.

## Open questions

1. **Where the browser comes back to.** There are two options:
   - **(a)** the portal: `<public_url>/oauth/callback`. Then
     `server.public_url` has to be set to a URL the operator's browser can
     reach.
   - **(b)** a loopback listener started by `siphon connect login` on the
     operator's machine. The CLI then hands the code to the daemon.

   Recommendation: (a). It works the same from the portal and the CLI and
   needs no second listener. Most authorization servers accept non-loopback
   https redirect URIs, and an http `localhost` URL works for a local
   install.
2. **Client registration.** There are three options:
   - dynamic registration, where the server allows it;
   - a pre-registered `client_id` and `client_secret` the operator supplies;
   - the client ID metadata document (CIMD).

   Recommendation: dynamic registration by default, with an optional
   pre-registered client in the source config (secret refs only) for
   servers that don't allow it. No CIMD yet: it needs Siphon to host a
   public metadata document, which can come later.
3. **How a source opts in.** There are two options:
   - an explicit `auth: { oauth: {} }` (plus optional
     `client_id`/`client_secret`/`scopes`);
   - auto-detection on the first 401.

   Recommendation: explicit. An unexpected 401 on a bearer source stays a
   plain error, and the config says what the source needs.
4. **Scope.** Should this cover stdio MCP servers or `http`-type sources?
   Recommendation: no. Only remote `mcp`-type sources, the ones the MCP
   authorization spec defines.
