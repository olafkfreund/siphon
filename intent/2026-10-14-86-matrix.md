# Intent: Matrix room events trigger rules, as an application service

## Problem

Matrix is "Not yet" in the catalog. A Matrix homeserver (Synapse, Conduit,
Dendrite) pushes events to an **application service** (AS): a URL listed
in a registration file the server admin installs. Siphon can't be one
today:

1. **Method and path.**
   - The homeserver sends
     `PUT <as-url>/_matrix/app/v1/transactions/{txnId}`.
   - It also sends `POST <as-url>/_matrix/app/v1/ping` (a health check),
     and may query `GET …/users/{userId}` and `GET …/rooms/{alias}`.
   - Siphon only routes `POST /hook/{source}`.
2. **Authentication.**
   - The homeserver sends the shared `hs_token` as
     `Authorization: Bearer <hs_token>`. Older servers put it in the query
     string as `?access_token=`.
   - Siphon's `token` mode reads a named header, but not a bearer
     `Authorization` header, which Siphon also strips from events.
3. **The answer.** Each transaction must get `200 {}`, or the homeserver
   retries it and eventually stops sending. Siphon answers `202` with no
   body.
4. **Batches.** A transaction is `{"events": [...]}` with many events.
   Rules need one event each.

## Proposed outcome

- **A Matrix source format** (`format: matrix` on a bearer-token mode).
  It's mounted at `/hook/<name>/_matrix/app/v1/…` and does four things:
  - **`PUT …/transactions/{txnId}`** checks the bearer, delivers each event
    in `events` as its own event (keyed by `event_id`), and answers
    `200 {}`. Retries of a transaction collapse, because the event ids
    repeat.
  - **`POST …/ping`** answers `200 {}` after the bearer check.
  - **`GET …/users/…` and `…/rooms/…`** answer
    `404 {"errcode":"M_NOT_FOUND"}`. Siphon doesn't create users or rooms.
  - **Anything else** gets 404.
- **A catalog entry, `matrix`.**
  - It generates the `hs_token` and the `as_token`, and prints a ready
    registration YAML for the homeserver (the `url`, both tokens, a
    `sender_localpart`, and namespaces), shown once.
  - The admin chooses which rooms (an alias regex) and users the AS is
    interested in.
- **A template:** a message containing "!deploy" in a room starts a
  routine.

## Affected users and systems

- Matrix homeserver admins and room users.
- `internal/web/web.go` (sub-path and PUT/GET routing for `/hook/`),
  `internal/source/webhook.go` (the format), `internal/config`, the
  catalog, docs and templates.

## Constraints

- **The bearer `hs_token` is compared in constant time,** never logged,
  and dropped from event headers. A query-string `access_token` is
  accepted only if the admin enables it (old servers), because tokens in
  URLs end up in logs.
- **Siphon never acts with `as_token` in this issue.** Sending messages
  back to Matrix needs the `as_token`, a secret, and no secret reaches a
  `cmd`. Replies are a follow-up, like the ServiceNow native action.
- **Room message content is untrusted.**
- **No new dependency.**

## Open questions

- **Should replies (posting into the room) be in scope?** **I'd leave them
  out.** Inbound is the hard part, and replies need either a native
  `matrix:` action or an agent with a Matrix MCP server. Ask again after
  this lands.
- **Should Siphon generate the registration file?** **I'd generate it,**
  shown once like other secrets. Writing it by hand is error-prone (tokens,
  regex namespaces).
- **The legacy `?access_token=` query auth:** off by default, with a
  source flag to allow it. **I'd do that.**
