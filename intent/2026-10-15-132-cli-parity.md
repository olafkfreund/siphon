# Intent: the CLI can do what the portal does

## Problem

The owner wants the CLI to cover every portal feature. A parity review of
main found that most portal features have a CLI command, but these do not:

1. **Deleting a login.** `siphon delete credentials X` removes only the config
   item and leaves the stored login secret and key file on disk. The portal's
   delete removes everything.
2. **Exporting the effective config from a remote server.** `config export`
   is local only.
3. **Full job detail.** `jobs show` returns only the database row: no routine
   steps, rendered prompt, reachable or blocked hosts, failure summary or
   notifications. Approving from the CLI means approving blind, because
   `get approvals` doesn't say what would run.
4. **Egress.** There is no API or CLI view of each agent's and rule's
   allowlist and the blocked hosts.
5. **Notion webhook verification.** It can't be completed without the
   portal.
6. **The dashboard's 24-hour numbers** (jobs, agent runs against the daily
   cap, success rate) are missing from `siphon status`.
7. **Testing an unsaved rule.** `siphon test` works on saved rules only.
8. **MCP tools.** `siphon mcp` lacks tools the CLI has: enable/disable,
   reset, history, restore, catalog, the notification log in `get`, and audit
   filters.

## Proposed outcome

- Each gap has a CLI command that follows the existing conventions
  (`-o json`, `--yes`, `--dry-run`, exit codes 0–5), backed by the API.
- Where possible, the API reuses the code that already serves the portal.
- `siphon mcp` gains the tools in point 8, under its existing write and
  secret gates.
- The docs (`cli.md`, `llm.md`) list the new commands and tools.

## Affected users and systems

- Operators and agents using the CLI or `siphon mcp`.
- The HTTP API in internal/web.

## Constraints

- **Admin token only, as for the rest of the API.** There are no new auth
  paths.
- **Approve/deny and connecting logins stay out of MCP** on purpose.
- **The Notion verification token stays secret-grade:** the API serves it
  with `Cache-Control: no-store`, and the CLI never logs it.
- **The deleted-login path removes exactly what the portal removes,** and
  writes the same audit entry.

## Open questions

None. The owner pre-approved this work.
