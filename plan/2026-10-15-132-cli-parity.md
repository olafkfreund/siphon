# Plan: the CLI can do what the portal does

## Approved decisions

- **Reuse the portal's functions.** Every new API endpoint serves the same
  function the portal page calls, so the two stay in step: `s.jobDetail`,
  `s.egress`, `s.approvalActions`, the dashboard numbers, and the rule-test
  core. Commands go through `internal/client` and follow the `cmd/siphon`
  conventions:
  - `-o json`;
  - `--yes` for destructive or secret-revealing actions;
  - exit codes 0 ok, 1 error, 2 usage, 3 validation, 4 not found,
    5 conflict.
- **Auth:** the admin token only, with no new auth paths.
- **MCP:** approve/deny and connect stay out.
- **The Notion token:** `Cache-Control: no-store`, never logged, and shown
  once.
- **Deleting a login** reuses `DELETE /api/connections/logins/{name}`
  exactly.
- **Not in scope:** role-scoped tokens, parsing `/metrics`, a new
  `delete login` verb.

## Steps

1. **Deleting a login.**
   - `cmd/siphon/guided.go`: in `connectLogin`, `--logout` with `--name`
     sends `DELETE /api/connections/logins/{name}`:
     - without `--yes`, it asks for confirmation on a TTY
       (`golang.org/x/term`, as other prompts do) and fails with exit 2
       otherwise;
     - a 404 exits with 4.
   - Update the flag help and the usage line in `cmd/siphon/cli.go`.
   - `siphon delete credentials <n>` prints a hint on stderr, pointing to
     `connect login --name <n> --logout`, if `GET /api/connections` shows a
     stored login with that name.
   - Tests: `cmd/siphon/guided_test.go`, against httptest. Check the method
     and path, that `--yes` is needed, and the exit code for a 404.
2. **Remote export.**
   - `cmd/siphon/cli.go`: remove `config` from `localOnly`. `clientMode`
     treats `config` like `jobs`, `approve` and `deny`: local if `-config`
     is among the args.
   - The client `config export` calls `GET /api/config/export` and prints
     `.yaml`, or the JSON object with `-o json`.
   - Make sure every other `config` subcommand without `-config` gives a
     usage error, not a client call. Check `cmd/siphon/main.go`, which has
     the `config` case at about line 122.
   - Tests: client mode prints the server's YAML; `-config` stays local.
3. **Job detail and approvals.**
   - `internal/web/pages.go`: add JSON tags (snake_case) to `jobView` and
     its nested step views. Replace the `Agent *config.Agent` field in JSON
     with `agent` (its name), using `json:"-"` plus a name field.
   - `internal/web/api.go`: `/api/jobs/{id}?detail=1` returns
     `s.jobDetail(id)`, with 404 as before.
   - `/api/approvals`: each row also gets `kind`, `target`, `source` and
     `source_type` from `s.approvalActions`. Wrap the row in a struct that
     embeds `store.PendingApproval`.
   - `cmd/siphon/verbs.go`:
     - `jobs show <id> --detail`: in text output, print the steps, prompt,
       hosts, failure summary and notifications;
     - `get approvals`: a WHAT column (`kind target`).
   - `cmd/siphon/mcp.go`: the `job` tool gets a `detail` bool.
   - Tests:
     - `internal/web/api_test.go`: detail JSON for a routine job includes
       the steps, and a secret in the config does not appear in the JSON;
     - approvals rows have `kind`;
     - the CLI shows the detail.

   Traps: the masking happens when `jobDetail` builds its result. Assert
   that a configured secret value never appears in the response body.
4. **Egress.**
   - `internal/web/pages.go`: add JSON tags to `egressView`, `egressList`
     and `egressBlocked`.
   - `internal/web/api.go`: `GET /api/egress` returns `s.egress()`.
   - `cmd/siphon/verbs.go`: add `egress` to `listKinds`, with a table:
     OWNER NAME ON HOSTS, then the blocked hosts.
   - The MCP `get` description lists `egress`.
   - Tests: the API shape; `get egress` text and JSON.
5. **Notion verification.**
   - `internal/web/notion.go`: `GET /api/sources/{name}/notion-verification`
     (`s.api`, the admin token):
     - it returns `{token, at}` with the header
       `Cache-Control: no-store`;
     - it returns 404 if there's no such source or nothing is pending.
   - `cmd/siphon/guided.go`: `connect notion <source> [--yes]`:
     - GET the token, print it with the instruction to paste it into
       Notion, then confirm (or `--yes`), then POST `{token}` to the
       existing endpoint;
     - a 404 exits with 4, and a 409 or a mismatch exits with 5.
   - Tests:
     - the GET header;
     - the 404;
     - the POST round trip using the pending token;
     - the token not in the slog output, with a test logger.
6. **Dashboard numbers.**
   - `internal/web/data.go`: extract
     `func (s *server) last24h() (dashStats, error)`, which returns
     `{Counts, Total, Running, Failed, AgentRuns, AgentCap, SuccessRate}`.
     `s.dashboard` uses it, and keeps the greeting and the bars.
   - `internal/web/api.go`: `GET /api/dashboard` returns `last24h`.
   - `cmd/siphon/verbs.go`: `fetchStatus` also fetches it. Status text gets
     a line `last 24h: N jobs (R running, F failed), agent runs A/C,
     success S`, and the JSON gets a `last_24h` object.
   - Tests: a seeded store gives the expected numbers; status JSON has
     `last_24h`.

   Traps: the time-based tests inject the clock through `s.Now`.
7. **Testing an unsaved rule.**
   - `internal/web/editors.go`: split the core of `runRuleTest`
     (parse the rule YAML → validate against the current config → evaluate
     against an event without saving) into a helper.
   - `internal/web/diagapi.go`: `POST /api/rules/{name}/test` takes an
     optional `rule` field (YAML). When it's set, the API uses the helper
     instead of looking up the saved rule.
   - `cmd/siphon/guided.go` (`buildTest`):
     `siphon test -f rule.yaml [event.json|-] [--last]`. The name comes
     from the file.
   - Tests:
     - an unsaved rule fires against the event;
     - an invalid rule exits with 3;
     - the store has no config change afterwards.
8. **MCP tools** (`cmd/siphon/mcp.go`). Each calls the same client function
   as its CLI command:
   - `enable` and `disable` (`rule`) and `reset` (`kind`, `name`): without
     `--allow-write` they report what they would do and change nothing;
   - `history` (`kind`, `name`, `rev`, all optional): read-only;
   - `restore` (`rev`): refused without `--allow-write`;
   - `catalog` (`category`, optional): read-only;
   - `get`: add `notifications` and `egress`, and pass the audit filters
     `rule`, `event`, `since` and `limit` through.

   Tests in `cmd/siphon/mcp_test.go`: each tool exists; the write gates
   hold (no API call without `--allow-write`); the audit filters reach the
   query string.
9. **Docs.**
   - Run `go generate ./docs`.
   - docs/llm.md: the MCP tool list gets the new tools.
   - docs/troubleshooting.md: one line each for `jobs show --detail` and
     `siphon get egress`.
   - docs/tasks/notion (or the Notion connection page): add the CLI path
     next to the portal one.
   - Verify that a second `go generate ./docs` changes nothing, and that
     `go test ./docs/...` passes.
