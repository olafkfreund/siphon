# Plan: Matrix room events trigger rules, as an application service

## Approved decisions

- **`format: matrix`** needs `signature: token` and
  `token_header: Authorization`. The header is compared, in constant time,
  as `Bearer <secret>`.
  - **`allow_query_token`** (matrix only, default false) also accepts
    `?access_token=`.
  - **`id`** isn't allowed.
  - **A failure** gets `401 {"errcode":"M_FORBIDDEN"}`.
- **Routes:** `PUT|POST|GET /hook/{source}/_matrix/app/v1/{rest...}` go to
  the same hook handler. Only a matrix source answers; others get 404.
- **`serveMatrix`:**
  - `PUT transactions/{txnId}`: validate `{"events":[obj with event_id]}`
    (else 400 `M_BAD_JSON`). For each event, run `Limit.Allow`
    (429 `M_LIMIT_EXCEEDED`), then `deliver` keyed by `event_id`
    (500 on error). Answer `200 {}`.
  - `POST ping` gets `{}`.
  - `GET users/*` and `GET rooms/*` get 404 `M_NOT_FOUND`.
  - Anything else gets 404 `M_UNRECOGNIZED`.
  - Answers are JSON, and none echoes request content. `authorization` is
    dropped from event headers.
- **Catalog `matrix`:**
  - fields `name`, `homeserver_name` (required), `rooms` (default `.*`)
    and `localpart` (default `siphon`);
  - it creates `<name>-hooks` (token / Authorization / matrix /
    `{{generated "hs_token"}}`).
  - The registration YAML, with a freshly generated `as_token` that isn't
    stored, is shown once.
- **The template `matrix-deploy-command`** (the `!deploy` stub), the docs,
  and "unencrypted rooms only".
- **Replies are out of scope.**

## Steps

1. **Config** (`internal/config/config.go`, `explain.go`, the schema).
   - **`format: matrix`** is validated per the decisions.
   - **`AllowQueryToken bool \`yaml:"allow_query_token"\``** is only allowed
     with matrix.
   - **Tests:**
     - valid matrix;
     - matrix with sha256;
     - matrix with `token_header: X-Foo`;
     - matrix with `id`;
     - `allow_query_token` without matrix.
   - **Verify:** `UPDATE_SCHEMA=1 go test ./internal/config` once, then
     `go test ./internal/config ./cmd/siphon`.

2. **Routing and handler** (`internal/web/web.go:172-181`,
   `internal/source/webhook.go`, `internal/job/hooks.go`).
   - **Routes:** register
     `PUT /hook/{source}/_matrix/app/v1/{rest...}`, and the `POST` and
     `GET` forms, to the existing `hook` func.
   - **The handler's method check** (`webhook.go:97`) allows `PUT` and
     `GET` only when `o.Format == "matrix"`. A matrix source answers a
     request whose path doesn't contain `/_matrix/app/v1/` with 404.
   - **The `token` case** gets the matrix bearer and query handling, then
     `serveMatrix`, entered like `serveEventGrid`. The single
     `Limit.Allow` is skipped for matrix.
   - **`WebhookOptions.AllowQueryToken`,** passed from `hooks.go`.
   - **Tests** in `webhook_matrix_test.go`, covering every case in the
     spec's verification list. Also a test in `internal/web` that `PUT` and
     `GET` on the new route reach the handler, and that a non-matrix source
     gets 404 there.
   - **Verify:** `go test -race ./internal/source ./internal/job ./internal/web`.
   - **Traps:**
     - A `GET` must not be blocked by PreLimit differently from a `POST`;
       treat them the same.
     - Never echo the bearer.

3. **Catalog, registration output, template and docs.**
   - **`internal/catalog`:** a new entry field,
     `registration: |` (a template).
     - Render it in `Render` after the items, with `data` plus
       `hook_url`, `hook_secret` (the bare `hs_token` the `generated`
       helper made) and `as_token` (`NewSecret()`, used only here).
     - Expose it as `Done.Registration`, shown once. The CLI's connect
       output and the portal's Done page print it under "Homeserver
       registration (save as a file, shown once)".
     - Find where `HookSecret` is printed (`cmd/siphon` connect, and the web
       Done template) and add it alongside.
   - **`services.yaml`:** the `matrix` entry, replacing `:854`, with the
     registration template from the spec. Add `TestMatrixEntry`: it renders
     with `homeserver_name: example.org`, the registration contains the
     `hs_token` that's stored as the secret and a different `as_token`, and
     the stored YAML has no `as_token`.
   - **`docs/templates/matrix-deploy-command.yaml`,** plus a `baseConfig`
     line, a README row, the entry's `templates:`, the webhook docs line,
     and `docs/llm.md`. Then run `go generate ./docs`.
   - **Verify:** `go test ./internal/catalog ./internal/web ./cmd/siphon ./docs`.
   - **Traps:**
     - The registration and `as_token` must not land in any stored item or
       the audit log.
     - The portal Done template must stay CSP-clean.

4. **All checks, and curl (mine).**
   - `go vet ./... && go test -race ./...`.
   - On a throwaway Siphon, curl:
     - a `PUT` transaction of 2 `m.room.message` events with the bearer
       (2 jobs);
     - the same again (no new jobs);
     - a ping;
     - a user query (404);
     - a wrong bearer (401).
