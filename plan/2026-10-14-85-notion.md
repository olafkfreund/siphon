# Plan: Notion page and database events, and Notion tools for agents

## Approved decisions

- **`format: notion`:**
  - it needs `signature: sha256`, `signature_header: X-Notion-Signature`
    and `signature_prefix: sha256=`;
  - with it, the secret may be empty, meaning "awaiting verification", with
    a validation warning.
- **The handler, with `format: notion` and no secret:**
  - **accepted:** exactly
    `{"verification_token":"secret_[A-Za-z0-9]{20,100}"}`, with no other
    keys. It calls `OnVerificationToken`, answers 200 with an empty body,
    and delivers nothing;
  - **anything else** gets 401 "awaiting verification token";
  - **with a secret,** the normal `sha256` path runs.
- **The pending token** is in memory on the Pipeline. Only the latest per
  source is kept, and it isn't persisted; Notion can resend it.
- **The portal and API:**
  - an operator sees the pending token and its age, with a "Use this
    token" button;
  - `POST /api/sources/{name}/notion-verification` (operator) stores the
    token as the source's write-only secret through
    `withSecrets`/`write`, with an audit row, then clears pending;
  - 404 with nothing pending, 409 when a secret is already set;
  - CSP-clean.
- **The catalog's `notion`:** an mcp source with
  `url: https://mcp.notion.com/mcp` and `auth: {oauth: {}}`, plus
  `<name>-hooks` (sha256 / X-Notion-Signature / `sha256=` /
  `format: notion`, no secret). The setup text marks the MCP OAuth as not
  yet verified.
- **The template `notion-page-summary`:** an agent with `mcp: [notion]`
  and default approval.

## Deviations

- **Step 3:**
  - **API authorisation:** the API route uses the API's bearer token. The
    API has no roles; only the portal route checks the operator role.
  - **Editing disabled:** `acceptNotion` returns 503 when config editing is
    disabled, like the other config routes.
  - **An audit row,** `notion_token_accepted`, is written on success.
- **Step 4:**
  - **`baseConfig` gains `server.public_url`,** which `auth.oauth` sources
    need.
  - **The template's agent is limited to read tools**
    (`mcp__notion__notion-fetch`, `mcp__notion__notion-search`), with a
    note to check the names against the server's tool list. A wrong name
    gives no tool, never a write.
  - **The template's category** is "Notifications & glue".
- **Rebased onto main after #97 (Discord):**
  - **The `format` switch, the explain entries and the tests** now carry
    both `discord` and `notion`.
  - **`llms-full.txt`** is regenerated.
- **Review of steps 1–4 (fresh Opus, one HIGH):**
  - **HIGH, fixed: the stored token is the one the operator saw.** Before,
    accept stored whatever was pending at click time, and an attacker could
    replace that by posting well-formed tokens. Now the portal form and the
    API body send back the shown token. It's compared in constant time
    with the pending one, and a mismatch or missing token gets 409 with
    nothing stored.
  - **HIGH, fixed: the setup order is reversed.** Paste into Notion and
    Verify first; only then use the token in Siphon. There's recovery text
    (delete `secret:`, Resend) and a restart note.
  - **MEDIUM, fixed:** the portal route maps code-0 errors through
    `apiError`, or 500, so it can't panic or leak raw errors.
  - **LOW, fixed:** the pending token is taken only when the commit is
    applied.
