## Wrong (the doc contradicts the code)

1. **README.md:684-686, session lifetime.** It says sessions last 24 hours "and survive logout until they expire or the daemon restarts". Since #119 they survive restarts: the key is kept in `<dir of server.db>/portal-session.key` (`cmd/siphon/main.go:521`, `internal/web/sessionkey.go:12`). Fix:
   > Sessions are HMAC-signed cookies (HttpOnly, SameSite=Strict) that last 24 hours (12 for SSO). They survive logout and restarts until they expire. To end every session, stop Siphon, delete `portal-session.key` next to `state.db`, and start it again (see [SSO](docs/tasks/sso.md#taking-access-away)). POSTs need a CSRF token.
2. **docs/tasks/routine.md:32-33, "Siphon has no clock source".** `type: schedule` sources exist, and `nightly-report.yaml:5-12` uses one with "no host timer needed". Fix:
   > **Schedules:** use a `type: schedule` source (`at: "0 6 * * *"`, `timezone:`), as `nightly-report` does. See [Run a task on a schedule](schedule.md).
3. **llms.txt:33** says "Routines: … schedules via a timer". Replace with "schedules via a `type: schedule` source".
4. **docs/llm.md:162-163.** It says that without an `id:`, identical events are deduplicated for 7 days. In fact `on: each` without `id` fails validation (`internal/config/config.go:1283-1285`), and since #111 ids are pruned by when they were last seen, measured against the rule's own activity (`internal/store/store.go:357-375`). Fix:
   > **`on: each` requires `id:`** (validation fails without it; schedule rules default it to `event.scheduled_at`). Each id fires once. It can fire again only after it has gone unseen for `server.retention.seen_events` (default 7 days), counted against the rule's own activity.
5. **docs/troubleshooting.md:32** (`fired` row) says "`on: each` fires once per `id` for 7 days". Replace with: "`on: each` fires once per `id`; an id that keeps coming back never fires again".
6. **docs/troubleshooting.md, `edge_already_true` row.** The doc describes it for `on: edge` only. The code also uses it for an `on: each` id that already fired (`internal/web/diagapi.go:305`). Append: "; or, for `on: each`, this event id already fired".
7. **docs/getting-started.md:179.** The sample `why` output shows `✓ source digest (webhook) is idle` next to a last event. A webhook source that has received an event reports `ok` (`internal/web/data.go:162-165`). Change it to `✓ source digest (webhook) is ok`.
8. **docs/troubleshooting.md, under "A run's units".** Cmd actions run in `siphon-action-open@` by default (`nix/module.nix:590`, `internal/action/template.go:87`), so the current `journalctl` line misses most cmd runs. Fix:
   > `journalctl -u 'siphon-action@*' -u 'siphon-action-open@*'` (runs with egress off, which includes cmd actions by default) and `journalctl -u 'siphon-mcp@*'` (MCP bridges).
9. **README.md:651-652, polkit.** It says siphon may "only start/stop/reset `siphon-action@<16 hex>` instances". The rule allows `siphon-(action(-open)?|mcp)@[0-9a-f]{16}` (`nix/module.nix:605`). Replace with: "only start/stop/reset its `siphon-action@`, `siphon-action-open@` and `siphon-mcp@` instances (16-hex ids)". Line 637 has the same problem ("a template unit, `siphon-action@.service`"); it should name all three templates.
10. **README.md:257 and 268, agent kinds.** "Three kinds exist" is wrong: the kinds are `claude|codex|agy|model` (`internal/config/explain.go:115`). Fix: "Four kinds exist: `claude` (default), `codex`, `agy` (Antigravity) and `model` (see [Model connections](#model-connections-ollama-and-openai-compatible-apis))". Change the comment on line 268 to `# claude (default) | codex | agy | model`.
11. **docs/concepts.md:105, cooldown.** It says cooldown is required only for agents. It is also required for ServiceNow writes and for routines that contain either (`config.go:1295-1299`). Fix: "It's required when the action is an agent, a ServiceNow write, or a routine containing either."
12. **docs/concepts.md:128.** The "API key" row lists `claude`, `codex` only, but agy takes `GEMINI_API_KEY` (README.md:354). Change it to `claude`, `codex`, `agy`.
13. **docs/concepts.md:76** says `siphon new task` "creates all three at once". It creates the source and the rule; the action is an inline `cmd` or refers to an existing agent or routine (getting-started.md:91 says "two items"). Fix: "`siphon new task` creates the source and the rule in one go."
14. **README.md:13-14** says "One YAML file is the only source of truth". Portal and CLI edits are stored as revisions in the database (concepts.md:151-156). Fix: "`siphon.yaml` is the operator's baseline; portal and CLI edits are stored as revisions on top of it, and one SQLite file holds the state."
