# Plan: Mattermost outgoing webhooks and slash commands trigger rules

## Approved decisions

These are carried over from the spec and the intent.

- **A webhook signature mode, `body-token`.**
  - **Reading and checking:** it reads `data[token_field]` (default
    `token`) from a JSON or form body, and compares it in constant time
    (SHA-256 of both sides, as `token` mode does). A missing, non-string or
    wrong token gets `401 "token missing or wrong"`.
  - **The token is deleted from the event,** and the replay key is
    `sha256(json.Marshal(data))` after the delete.
  - **`reply_text`:** when set, an accepted delivery gets `200`,
    `application/json`, `{"text": reply_text}`. Otherwise it's `202` and
    empty, as for every other mode.
- **Source fields:** `token_field` (`^[A-Za-z_][A-Za-z0-9_]*$`) and
  `reply_text` (≤500 chars). They're only allowed with `body-token`, and
  `body-token` refuses `signature_header`, `timestamp_header` and
  `token_header`.
- **Form decoding for every webhook source:** with
  `Content-Type: application/x-www-form-urlencoded`, `url.ParseQuery`
  gives a `string` per single value and a `[]any` per repeated key.
  Anything else stays as today (JSON, or `{"raw": …}`).
  - Nothing in the repo matches `event.raw` today; checked with grep.
- **The `mattermost` catalog entry is available:**
  - it creates `<name>-hooks` with `signature: body-token`;
  - the required `token` is pasted in, and an optional `reply` sets
    `reply_text`;
  - the setup text gives the URL up front (`<public URL>/hook/<name>-hooks`),
    because Mattermost shows the token only after its integration is saved.
- **The generic `webhook` entry** gains the mode choice `body-token`.
- **The `mattermost-command-agent` template:**
  - the agent's answer is posted to a Mattermost incoming webhook, with the
    JSON string built by `printf "%q"`;
  - the repo has no `json` template function;
  - `%q`'s `\x..` escapes for control characters aren't valid JSON, so the
    template carries a shortcut comment about it.

## Deviations

- **Step 1:**
  - **No schema enum change.** The schema has no enum for `signature`; it's
    a string, so only the two new fields appear in it. `explain` lists
    `body-token`.
  - **A validation warning for `body-token`,** matching `token` mode's: the
    secret travels in every body, and a captured delivery can be replayed.
- **Step 2:** `decodeBody` returns `any`, not `map[string]any`, so a JSON
  array or scalar body keeps working in the other modes. In `body-token`,
  a non-object body has no token and gets 401.
- **Step 4:**
  - **The template rule** sets `id: event.trigger_id` (`on: each` needs an
    id). The rule only matches slash commands, which always carry a unique
    `trigger_id`.
  - **`TestExplainCommand`'s expected signature enum** now includes
    `body-token`.
  - **`docs/cli.md`** gained the generated `--reply` flag.
- **Review of steps 1–4 (fresh Opus, no HIGH or MEDIUM findings):**
  - **`reply_text`'s limit** counts characters (`utf8.RuneCountInString`),
    not bytes.
  - **New tests:** a repeated form `token` is refused, and a repeated JSON
    `token` leaves no token in the event.
  - **The template's `%q` shortcut comment** now names every escape that
    isn't valid JSON.
  - **The catalog `reply` help** says an outgoing webhook posts the reply
    in the channel.
  - **Release note:** form bodies become fields instead of `{"raw": …}`.
    It's in the PR description.
  - **Left as is:** a form body that `url.ParseQuery` rejects (a stray `;`)
    still falls back to `raw` in modes other than `body-token`.
- **After rebasing onto main (#92, #91 merged):**
  - **Conflicts resolved** by keeping both sides in `baseConfig` and the
    templates README, and regenerating `llms-full.txt`.
  - **`TestNotYetServicesCannotConnect`** asserted at least 9 not-yet
    entries. With Opsgenie removed (#91) and Mattermost available, there
    are 8. The guard now only requires that the loop checked something,
    since the count keeps falling as the #90 services ship.
