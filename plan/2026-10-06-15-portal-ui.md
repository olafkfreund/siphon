# Plan: Portal: a proper, usable UI, with editing (Siphon)

**Precondition:** #16 (rename to Siphon) is merged (PR #17, 2026-10-06); this branch is rebased on it.
below are post-rename: `cmd/siphon`, `services.siphon` and the
`siphon_session` cookie. Rebase this branch on main after #16.

## Approved decisions (self-contained)

- **Brand "Deep Current".**
  - The reference is `docs/brand/README.md` plus the mockups in
    `docs/mockups/portal.html`. **The mockups are the visual contract.**
  - Tokens: `abyss #06111F`, `deep #0E2A47`, `ink #7C5CFF`, `current #3B82F6`,
    `biolume #2EE6D6`, `kelp #34D399`, `amber #FFB547`, `coral #FF5D73`,
    `shallows #F3F8FB`. The gradient is `ink → current → biolume` at 135°.
  - **Shallows** (light) and **Abyss** (dark) follow
    `prefers-color-scheme`, with a manual toggle stored in `localStorage`.
  - Cards have a 14 px radius and neutral shadows (no coloured glow).
  - System UI font; a monospace font for code, with ligatures off.
  - Status pills combine an icon, a label and a colour.
  - Flow view: source → condition → action. The current's dashes animate
    while enabled. Bubbles are the live and empty-state motif.
  - Motion is 200–400 ms, and is off under `prefers-reduced-motion`.
  - Desktop has a sidebar in groups; a phone gets a top bar and full-width
    Approve/Deny.
  - Ocean flavour appears only in empty states and the tagline.
- **Pages:**
  - Login
  - Dashboard `/`
  - Jobs
  - Job detail (what will run, triggering event, output, blocked egress
    hosts with "allow", routine timeline)
  - Approvals
  - Rules (flow cards and an enable switch)
  - Rule editor (form, YAML tab, diff, live tester)
  - Sources, Agents and Routines (list and editor)
  - Logins (metadata and paste-to-add)
  - Egress (effective lists and recently blocked)
  - Audit
  - History (revisions, diff, restore, export)
- **Editing is an overlay on the file.**
  - SQLite tables `config_item(kind, name, yaml, deleted, updated_at)` and
    `config_revision(id, at, actor, summary, items_json, diff)`.
  - Kinds: `sources`, `agents`, `routines` and `credentials` are maps;
    `rules` is a list keyed by name. **`server`, `limits` and `units` can
    never be edited.**
  - Effective config = the file's YAML node tree plus the overlay, run
    through the existing `config.Parse`, `Validate` and `Warnings` (one
    parser).
  - Provenance is `file`, `portal` or `override`; "Reset to file" deletes
    the overlay row.
  - **Saving:** validate the candidate, show the diff, then confirm, which
    writes the item, the revision (full snapshot and unified diff, secrets
    as refs) and an audit `config_changed` row, then applies. Saving
    against a stale revision gets "changed since you opened it".
  - Restoring a revision is itself a new revision.
  - `siphon config export` prints the effective YAML.
  - **Startup:** if the overlay is invalid, `serve` uses the file plus the
    last valid revision, logs the error and shows a red banner.
    `validate` reports it; `validate -file-only` checks the file alone.
- **Hot apply.**
  - `Pipeline` holds an `atomic.Pointer[config.Config]`, read with
    `Config()`. Each poll and job takes one snapshot for its whole run.
  - `Apply(cfg)` swaps the pointer, restarts the pollers' generation (a
    context per generation) and rebuilds the webhook map.
  - Jobs keep their payload snapshots. Web reads config through an
    accessor.
- **Secrets are write-only.**
  - A secret field takes an `env:`/`file:` ref or a value. A value is
    written to `<state>/secrets/<kind>-<name>-<field>` (file 0600, dir 0700)
    and the item stores `file:<path>`. Values are never rendered back:
    the page shows "•••• set (stored)".
  - Logins use the same code path as `credentials import`.
  - Values stay in `cfg.Secrets()` for masking.
- **Rule tester.**
  - Each source's last event (after extraction, capped at 64 KiB, keys
    matching `token|secret|password|authorization|api_key|cookie`
    case-insensitively redacted) goes in `source_state.json`.
  - The tester is the `rules test` dry-run (an in-memory store) plus prompt
    and argv rendering, and never enqueues.
  - htmx `input changed delay:400ms`.
- **Live updates.** Polling by fragment: the dashboard every 5 s; a running
  job's header and output every 2 s, then stopped; the approvals badge
  every 10 s. **Editors never poll.**
- **Unchanged constraints:**
  - CSP `default-src 'self'`: **no inline `<script>`, no `<style>` and no
    `style=""` attributes** (the mockup uses them; production must not);
  - CSRF on every POST;
  - a single binary (embed.FS), with no build step and no external origins;
  - essential paths (login, approve, deny) work without JS;
  - write actions are audited;
  - JSON API parity under `/api/config/...` (same validation, bearer
    token).

1. **Store.**
   - Add `internal/store/migrations/0002_config_overlay.sql` with the two
     tables and `config_revision(at)` as the index.
   - Add queries: `ConfigItems(db)`, `PutConfigItem(tx, kind, name, yaml,
     deleted)`, `DeleteConfigItem`, `AddRevision(tx, actor, summary,
     itemsJSON, diff) (id)`, `Revisions(db, limit)`, `Revision(db, id)`,
     `LatestRevision(db)`. Writes go inside `BEGIN IMMEDIATE`.
   - Set `SetSourceEvent(db, source, json)` where polls and webhooks
     already record `source_state`, after extraction. Cap it at 64 KiB
     (beyond that, store `{"_truncated":true}`). Apply the redaction
     helper (`redactKeys(any) any`, recursive).
   - **Tests:** the migration applies on an existing DB; CRUD;
     redaction (nested, case-insensitive); the cap.
   - **Trap:** migrations are numbered and embedded; never edit `0001`.
2. **Overlay** (`internal/config/overlay.go`).
   - `type Item struct{Kind, Name, YAML string; Deleted bool}`.
   - `Effective(file []byte, items []Item) ([]byte, map[Key]Provenance, error)`:
     parse the file into a `yaml.Node`; for each item, set or remove the
     map key (or replace, append or remove a rule by `name`); marshal.
   - `Kinds` is the editable allowlist. Any other kind is an error.
   - `LoadWithOverlay(path, items)` = `Effective`, then `Parse`, with the
     relative DB resolved against the file's directory, as `Load` does.
   - `Export(cfg bytes)` passes the bytes through, already normalised.
   - **Tests:** every kind; rule replace, append and remove; a tombstone
     for a file item; `server`/`limits`/`units` refused; provenance;
     an effective config with no overlay round-trips byte-equal through
     `Parse` (semantically equal structs).
   - **Trap:** keep key order and comments where possible (node-level
     edits), so the export diffs cleanly.
3. **Hot apply.**
   - `Pipeline.cfg atomic.Pointer[config.Config]`, with `Config()` and
     `Apply(*config.Config)`.
   - Replace every `p.Cfg` read in `internal/job` with one `cfg :=
     p.Config()` at the top of each entry point (`HandleEvent`, `runJob`,
     `agentExec`, `pollLoop` iteration, `egressFor`, `Webhooks` handler),
     and pass it down.
   - `Serve`'s poller spawn moves into `startPollers(ctx, cfg) (stop func())`,
     and `Apply` calls stop, then start.
   - `Webhooks()` returns a handler that looks up the current config's
     webhook source per request, instead of a fixed map.
   - `web.Options.Cfg` becomes `Config func() *config.Config`, plus
     `Apply func(*config.Config) error`.
   - **Tests:** a rule added through `Apply` fires on the next event; a
     removed source stops polling (a fake clock or a short poll interval);
     a job already queued keeps its snapshot; `-race` is clean.
   - **Trap:** `Pipeline{Cfg: ...}` literals in tests and in `cmd` change
     to `job.New`. Keep the `Cfg` field only if needed for tests; prefer
     removing it.
4. **CLI.**
   - `load()` reads the overlay items from the DB, if the DB exists, for
     `serve`, `run-once` and `validate`.
   - `validate -file-only` skips the overlay.
   - `siphon config export -config f` prints the effective YAML.
   - On an invalid overlay, `serve` falls back to the file plus the last
     valid revision's `items_json`, logs the error, and sets
     `web.Options.Banner`.
   - **Tests:** the fallback; the export with a portal-only rule; `-file-only`.
5. **Design system** (Opus).
   - `static/style.css` holds the tokens, base, sidebar/topbar, card, btn,
     pill, chips, table (cards on phone), forms, seg, tabs, flow, toast,
     empty and utilities, ported from the mockup's CSS, **minus every
     inline style**: utility classes replace `style=""`.
   - `static/app.js` (no framework, deferred) handles:
     - the theme toggle and persistence;
     - the menu toggle;
     - copy buttons;
     - toast auto-dismiss;
     - argv and step list add/remove/reorder;
     - `g d`/`g j`/`g r` and `/`;
     - the `aria-live` announce on `htmx:afterSwap`.
   - `static/icons.svg` is a sprite holding the mockup's symbols, used via
     `<use href="/static/icons.svg#i-…">`.
   - `static/mark.svg` and `static/mark-bare.svg` are copied from
     `docs/brand`; the favicon is `mark.svg`.
   - `layout.html` gets the sidebar, topbar, banner and toast region.
   - The login and dashboard templates follow the mockup.
   - Dashboard data:
     - counts by state over 24 h (`store.JobCounts(since)`);
     - agent runs today (the existing cap query);
     - pending approvals with their action summary;
     - failed in the last 24 h;
     - source health: `ok` if the last poll is under 2× the interval and
       there is no error, `stale` past that, `error` if `last_error` is
       set; webhooks show the last delivery;
     - recent jobs.
   - **Tests:** pages render; **no `<script>` without `src`, no `<style>`,
     and no `style=` in any template** (a grep test); CSP is unchanged;
     the static files are served.
6. **Read pages** (coder): jobs, job detail, approvals, audit, egress,
   logins (read), and sources (read), restyled per the mockup.
   - **Job detail:**
     - The "what will run" panel comes from `action_json` (agent name,
       kind, login, limits, the rendered prompt from the payload env, the
       egress list via `AgentEgress(snapshot)`), or the argv or unit.
     - The triggering event comes from `payload.env.event`, redacted with
       the step 1 helper.
     - Output goes in a `<pre>`.
     - Blocked hosts are parsed from `egress: blocked (\S+) \((\d+)\)`
       lines.
     - Routine steps form a timeline.
   - **Fragment polling:** each block has its own `hx-get` partial route
     (`/fragments/...`), and `#main` no longer polls as a whole.
   - **Tests:**
     - each page renders;
     - the job detail shows the prompt;
     - the redacted event hides `api_key`;
     - the blocked-hosts list is parsed;
     - no stored secret value appears anywhere (seed one and grep every
       response).
7. **Write paths** (coder).
   - One generic handler set over kind: `GET /config/{kind}`,
     `GET /config/{kind}/new`, `GET /config/{kind}/{name}`, and
     `POST /config/{kind}/{name}/check` (validate plus diff, no write).
     The rest of the routes:
     - `POST …/save` (needs `rev`; stale gives 409 plus the reload message);
     - `POST …/delete`;
     - `POST …/reset`;
     - `GET /history`;
     - `GET /history/{id}`;
     - `POST /history/{id}/restore`;
     - `GET /history/export`.
   - Per-kind form ↔ YAML mapping lives in `internal/web/forms.go`, with
     explicit fields per kind (spec table). The YAML tab posts the raw
     item YAML.
   - Secret fields: an empty value keeps the current one. A ref is stored
     as is. A value is written to the secrets file and becomes `file:`.
   - Logins: `POST /logins` (name, provider, pasted login or API key) goes
     through the same function as the CLI import (factor it out of `cmd`
     into `internal/cred` if needed). `POST /logins/{name}/delete`.
   - Every POST checks CSRF and writes an audit row with the diff (refs
     only).
   - The API mirrors these under `/api/config/...` with JSON bodies.
   - **Tests:**
     - create, update, delete and reset for each kind;
     - an invalid item comes back with the field errors and nothing stored;
     - a stale revision gets 409;
     - restore;
     - export;
     - a secret value is stored 0600 and never appears in the page, the
       diff, the export or the audit;
     - `server`/`units` are refused through both the HTML and the API;
     - CSRF is required.
8. **Editors** (coder).
   - **Rule editor:** the form per the mockup (source picker, condition,
     edge/each and id/for_each/repeat, cooldown, approval, action tabs) and
     the live tester at `POST /rules/test` (candidate rule plus last event
     or pasted JSON → match list, rendered prompt/argv/unit, errors). The
     flow cards are on the rules list.
   - **Source editor:** by type (mcp: url or command, read resource or
     tool and args, poll, allow_private, auth; http: url, method,
     headers with a secret flag per header, poll; webhook: secret,
     signature preset, id, timestamp header), plus a health and
     last-event preview.
   - **Agent editor:** kind, login picker, command override, prompt,
     MCP multi-select, allowed tools as chips, limits, approve, and egress
     enabled/allow, with the **effective allowlist recomputed live**
     (`POST /agents/egress-preview`).
   - **Routine editor:** ordered steps, each step with kind, if, retry,
     timeout, approve and continue_on_error.
   - **Tests:** the tester never enqueues (jobs count unchanged); the
     rendered prompt is correct; the egress preview matches
     `AgentEgress`; each editor round-trips YAML → form → YAML with no
     change.
9. **Visual check** (Opus).
   - Run the local instance (`~/.local/state/siphon-dev`), seeded with the
     mockup's sample rules.
   - Screenshot every page in light, dark and at phone width (headless
     Chrome), compare with the mockups and fix the differences.
   - Check keyboard navigation and focus rings, contrast in both themes,
     and reduced motion.
10. **VM subtest and PR** (Opus).
    - VM subtest: create a rule through `/api/config/rules`, then fire its
      webhook and see the job without a restart; and an invalid item gets
      400 and no change.
    - Then a fresh Opus security review (auth/CSRF on the new writes,
      secret handling, overlay `server`/`units` refusal, tester
      side-effects, XSS through config values in the templates).
    - Then the PR with screenshots, CI green.

## Rollback

Revert the merge. The overlay tables stay in the DB, unused (harmless).
The file config alone keeps working, since the overlay only adds to it.
An operator can also drop portal edits without reverting: delete all
items and restore an empty overlay from History, or use
`siphon config export` first to keep them.

## Deviations log
- **Step 1 (coder):**
  - `PutConfigItem` and `AddRevision` take `now` (store convention).
  - The revision type is `ConfigRevision`, since `Revision` is the function name.
  - There is no `BEGIN IMMEDIATE`: the store has a single connection, so writes are already serialized.
  - `RedactKeys` is exported for reuse in step 6.
  - Webhook last events are written in `deliver`, which runs only after HMAC verification. Polls write theirs in `Tick`.
- **Step 5 (Opus):**
  - The icon sprite is inlined in the layout (`sprite.html`) instead of a separate `icons.svg`, which avoids external `<use>` loading issues.
  - The nav shows only pages that exist now; Agents, Routines, Logins, Egress and History join with steps 6–8.
  - The dashboard's Approve/Deny are plain forms that return to `/` (a `back` field in `afterPost`).
  - Webhook sources show "waiting for a delivery" until their first delivery.
- **Step 6** was done by **Opus**, not the coder, so it could run in parallel with the coder's steps 2–4.
  - **Polling:** whole pages, with a per-page `Poll` flag: lists poll, and the job detail polls only while queued, running or waiting. This replaces separate `/fragments/...` routes; editors never poll. Fragment routes were dropped as unneeded.
  - **Search:** no search box on Jobs yet; state chips with counts cover filtering.
  - **Prompt rendering:** `action.RenderPrompt` was factored out of the agent runner and is shared with the job page (and step 8's tester).
  - **Payload:** `store.JobPayload` reads a job's payload for the job page.
  - **Redirects:** approve/deny can return to the dashboard or the job page (`back`, matched against `^/(jobs/[0-9]+)?$`, never an arbitrary URL).
  - **Read-only pages:** Logins and Egress exist now. Adding logins and the "allow for agent" buttons come with the write paths (steps 7–8).
- **Step 2 (coder):**
  - There is no `store.ConfigItem → config.Item` helper (the types differ), so the caller maps them.
  - No `Export` pass-through: `Effective`'s output is the export.
  - `Load` and `LoadWithOverlay` share `resolveDB`.
  - Replacing an item drops that item's own inline comments; comments elsewhere survive.
- **Step 3 (coder):**
  - `Webhooks()` returns a per-request lookup (`func(source) http.Handler`), so sources added by `Apply` take webhooks immediately. Unknown sources get 404.
  - The worker count and the egress listener stay fixed at startup: `server.*` can't be edited, and the egress proxy starts lazily for new agents.
  - `Apply` holds its mutex while the old pollers drain, which is bounded by one poll's HTTP timeout.
  - Step 2 follow-up: a rule item whose YAML `name` differs from the item name is rejected.
- **Step 4 (coder + Opus):**
  - `-file-only` works on every `load` command.
  - `rules test` also sees portal edits.
  - `items_json` is a JSON array of `store.ConfigItem` (step 7's revision writer must produce that shape).
  - The DB is opened with `store.Open`, and is never created when it's missing.
  - **The NixOS unit's `ExecStartPre` uses `validate -file-only`.** Otherwise a bad portal edit would stop the service from starting, instead of serve falling back with a banner.
- **Step 7 (coder):**
  - The routes are as planned, plus `POST /api/config/{kind}/{name}/reset`.
  - `web.Options.ConfigPath` is set by serve, and the write routes give 503 without it.
  - The login import goes through one function, `cred.ValidateImport`, which the CLI and the portal share; `cred.Store.Delete` is new.
  - Secret fields are webhook `secret`, `auth.bearer` and credential `api_key`. Raw YAML with an inline secret is rejected by validation.
  - Secret file names are built only from names matching `^[A-Za-z0-9][A-Za-z0-9_.-]{0,63}$` (Opus checked for path traversal).
  - Saving through the form keeps the keys the form doesn't cover. Routines are edited in the YAML tab only.
- **Step 8 (coder):**
  - The dry run is `rule.DryRun` in `internal/rule`: an `internal/job` home would make an import cycle with `web`. `siphon rules test` uses it too.
  - `config.Config.NeedsApproval` is now the single approval rule.
  - Form and YAML are stacked cards until step 9 adds the tab switching in `app.js`.
  - The tester doesn't fully validate; Save does.
  - Form saves write item YAML with sorted keys.
- **Step 9 (Opus):**
  - Config pages have human titles ("Edit rule ask-claude", "New source"), breadcrumbs, and provenance badges ("from siphon.yaml", "added in the portal", "overrides siphon.yaml").
  - The nav gained Agents, Routines and History, and config pages light up their kind.
  - YAML editing is a collapsible "Edit as YAML" section (`<details>`, no JS) instead of tabs.
  - The live tester was checked against the running server: match and no match, the rendered prompt, and "waits for approval".
- **Step 10, security review fixes (fresh Opus reviewer; fixed by the coder; verified by Opus with the race tests and all 12 VM subtests).** Principle: a portal or API token holder cannot widen host privileges.
  - **F1 (critical):** a stdio MCP source `command` runs in the daemon, unsandboxed, so it can only be set in `siphon.yaml`.
  - **F2 (high):** the `env:`/`file:` refs of an overlay item may only be its own stored secrets (`secrets/<kind>-<name>-*`) or the unchanged ref from `siphon.yaml`. This also covers an agent's `api_key_file`. Resolution errors no longer reveal whether a file exists.
  - **F3 (high):** `allow_private` is file-only, and `siphon.service` gets `IPAddressDeny = metadataDeny`.
  - **F4:** anchors and aliases are rejected in items. As a backstop, server, limits and units must equal the file's.
  - **F5:** secrets are written only by `commit`, after the stale check and validation, atomically (`O_EXCL|O_NOFOLLOW` then rename), 0600, into a 0700 dir that must not be a symlink. Review writes nothing.
  - **F6:** the startup fallback is the file plus tombstones, so deletions are kept. The useless last-revision tier is removed.
  - **F7:** `writeSecret` validates the name itself.
  - **F8 (Opus):** an overlay can't set an agent's `egress.enabled: false` unless the file does; adding hosts to `egress.allow` stays allowed.
  - **Kept, as decided:** an overlay agent may set `command`/`runner`, which runs in the `siphon-action@` sandbox.
- **Step 9, second visual pass (owner request: "use codex to review the layout and theme"; also run icons, provider icons, a more visual rule editor, easier logins).**
  - **The Codex review** (read-only, ChatGPT login, 14 screenshots) gave 14 suggestions plus 3 signature ideas. Implemented:
    - dashboard wording ("Needs attention", failures in the subtitle);
    - a contrast-safe primary gradient and `--link` token;
    - an accessible phone menu (`aria-expanded`, Escape, focus return);
    - phone tables as cards (`data-label`) and compact "Needs" rows (44px targets);
    - side panels aligned to the top;
    - tester paste fields hidden for "Last event";
    - advanced fields folded under "More options";
    - flow lines that stack in narrow cards (container query);
    - a failure summary on the job page, and the rule linked to its editor;
    - a full-width logins form;
    - honest egress wording;
    - History rows "Review" before restore, with the diff coloured;
    - tabular numbers;
    - signature ideas: the jet's bubbles on running pills, and a quiet deep-water header wash.
    - **Not done:** the "pulse on a new run" idea, which needs per-rule change tracking.
  - **Runs** show a kind icon (agent, command, unit, routine) and, for agents, a provider badge. `store.ListJobActions` reads the provider from the job's agent snapshot, falling back to the live config.
  - **Provider badges** are original monograms in each provider's colour (Claude, Codex, agy), **not vendor logos** (trademarks). The owner can add official marks if their brand terms allow it.
  - **Rule editor:** numbered Watch → When → Then steps with icons, icon segmented controls (On change / Every event; Agent / Command / Unit / Routine), a cooldown icon, and the approval toggle.
  - **Logins:** an account card per login with a status (Connected, Expires, Expired, Not connected, API key) and Connect/Replace/Delete, where Delete asks to confirm (`data-confirm` in `app.js`). Add/Connect uses provider tiles with only the choices that apply and the exact command to run, works without JS (`:has()`), shows errors inline (422, the value never echoed), and confirms on success.
